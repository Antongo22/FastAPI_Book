Глава 11: Авторизация Socket.IO

JWT в Socket.IO auth payload, отказ в connect и события от подтверждённого пользователя.

Порт: 8011 Swagger: http://localhost:8011/docs Результат: После главы вы умеете принимать Socket.IO-подключение только с валидным JWT и не доверять username из клиента.

Что разбираем в этой главе

  • Socket.IO auth - объект, который клиент передаёт при подключении: { access_token: token }.
  • connect event - место, где сервер решает принять или отклонить подключение.
  • return False - способ отказать Socket.IO-клиенту при невалидном token-е.
  • JWT claims - username и роль можно брать из подписанного token-а.
  • Authorized event - каждое сообщение содержит пользователя, которого подтвердил сервер.

Как проходит запрос

  1. Клиент получает access token через /api/auth/login.
  2. Клиент подключается к Socket.IO endpoint-у /socket.io и передаёт token в auth.
  3. Сервер декодирует JWT и проверяет подпись и срок действия.
  4. Если token плохой, обработчик connect возвращает False, и Socket.IO отказывает клиенту.
  5. Если token валиден, сервер сохраняет sid -> username и отправляет событие authorized.
  6. Событие authorized_message берёт username из серверного словаря, а не из клиентского payload.

Endpoint-ы для проверки

POST /api/auth/loginДемо-выдача access token-а.
GET /api/socket/infoКоличество авторизованных Socket.IO-подключений.
Socket.IO /socket.ioЗащищённые события authorized и authorized_message.

Ключевой фрагмент

{% raw %}import os
from datetime import datetime, timedelta, timezone

from fastapi import FastAPI, HTTPException
from jose import JWTError, jwt
from pydantic import BaseModel
import socketio


SECRET_KEY = os.getenv("JWT_SECRET_KEY", "fastapi-book-development-secret")
ALGORITHM = "HS256"


sio = socketio.AsyncServer(async_mode="asgi", cors_allowed_origins="*")
fastapi_app = FastAPI(title="Глава 11: Auth Socket.IO")


class LoginRequest(BaseModel):
    username: str
    password: str


def create_access_token(username: str) -> str:
    expires = datetime.now(timezone.utc) + timedelta(minutes=30)
    return jwt.encode({"sub": username, "exp": expires}, SECRET_KEY, algorithm=ALGORITHM)


def verify_token(token: str) -> str:
    try:
        payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
        return str(payload["sub"])
    except (JWTError, KeyError) as error:
        raise HTTPException(status_code=401, detail="Invalid token") from error


def authorize_socketio(auth: dict | None) -> str | None:
    token = (auth or {}).get("access_token") or (auth or {}).get("token")
    if not token:
        return None
    try:
        return verify_token(str(token))
    except HTTPException:
        return None


@sio.event
async def connect(sid, environ, auth):
    username = authorize_socketio(auth)
    if username is None:
        return False
    authorized_clients[sid] = username
    await sio.emit("authorized", {"sid": sid, "username": username}, to=sid)


app = socketio.ASGIApp(sio, other_asgi_app=fastapi_app, socketio_path="socket.io"){% endraw %}

Если совсем по-простому

Socket.IO-подключение тоже нужно защищать. Иначе любой клиент сможет отправлять события в чат.

Token передаётся при подключении в объекте auth. Сервер проверяет token прямо в событии connect.

Username берётся из JWT и хранится на сервере по sid, чтобы клиент не мог притвориться другим пользователем.

Что здесь важно

  • Важно проверять token в connect, до обработки любых пользовательских событий.
  • Клиенту нельзя доверять username из сообщения: он должен быть взят из JWT.
  • Token передаётся в Socket.IO auth payload, а не в query string raw WebSocket URL.

Типичные ошибки новичков

  • Передавать token в query string raw WebSocket URL, хотя в этой главе используется Socket.IO auth payload.
  • Брать username из события клиента вместо JWT.
  • Проверять token только на первом HTTP login, но не проверять его при real-time подключении.

{% raw %}import os
from datetime import datetime, timedelta, timezone

from fastapi import FastAPI, HTTPException
from jose import JWTError, jwt
from pydantic import BaseModel
import socketio


SECRET_KEY = os.getenv("JWT_SECRET_KEY", "fastapi-book-development-secret")
ALGORITHM = "HS256"

fastapi_app = FastAPI(
    title="Глава 11: Auth Socket.IO",
    description="JWT protected Socket.IO",
    version="1.0.0",
    docs_url="/docs",
    redoc_url="/redoc",
)
sio = socketio.AsyncServer(async_mode="asgi", cors_allowed_origins="*")


class LoginRequest(BaseModel):
    username: str
    password: str


def create_access_token(username: str, role: str = "user") -> str:
    expires = datetime.now(timezone.utc) + timedelta(minutes=30)
    return jwt.encode({"sub": username, "role": role, "exp": expires}, SECRET_KEY, algorithm=ALGORITHM)


def verify_user_token(token: str) -> dict:
    try:
        payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
        return {"username": str(payload["sub"]), "role": str(payload.get("role", "user"))}
    except (JWTError, KeyError) as error:
        raise HTTPException(status_code=401, detail="Invalid token") from error


def authorize_socketio(auth: dict | None) -> dict | None:
    token = (auth or {}).get("access_token") or (auth or {}).get("token")
    if not token:
        return None
    try:
        return verify_user_token(str(token))
    except HTTPException:
        return None


authorized_clients: dict[str, dict] = {}


@fastapi_app.post("/api/auth/login")
async def login(request: LoginRequest):
    if not request.username or not request.password:
        raise HTTPException(status_code=401, detail="Неверное имя пользователя или пароль")
    role = "admin" if request.username == "admin" else "user"
    return {
        "access_token": create_access_token(request.username, role),
        "token_type": "bearer",
        "username": request.username,
        "role": role,
    }


@fastapi_app.get("/api/socket/info")
async def socket_info():
    return {
        "authorized_connections": len(authorized_clients),
        "users": [user["username"] for user in authorized_clients.values()],
    }


@sio.event
async def connect(sid, environ, auth):
    user = authorize_socketio(auth)
    if user is None:
        return False
    authorized_clients[sid] = user
    if user["role"] == "admin":
        await sio.enter_room(sid, "admins")
    await sio.emit("authorized", {"sid": sid, **user}, to=sid)


@sio.event
async def disconnect(sid):
    authorized_clients.pop(sid, None)


@sio.event
async def authorized_message(sid, data):
    user = authorized_clients.get(sid)
    if user is None:
        return
    await sio.emit("authorized_message", {
        "event": "authorized_message",
        "sid": sid,
        "username": user["username"],
        "message": data.get("message", ""),
    })


@sio.event
async def admin_message(sid, data):
    user = authorized_clients.get(sid)
    if user is None or user["role"] != "admin":
        await sio.emit("forbidden", {"reason": "admin role required"}, to=sid)
        return
    await sio.emit("admin_message", {
        "from": user["username"],
        "message": data.get("message", ""),
    }, room="admins")


app = socketio.ASGIApp(sio, other_asgi_app=fastapi_app, socketio_path="socket.io"){% endraw %}

3. Как проверить

Socket.IO connectОбычный пользователь подключается с auth: { access_token }.
Socket.IO admin_messageОбычный пользователь получает событие forbidden.
Socket.IO admin_messageAdmin получает событие admin_message.

Полный разбор ответа

Ниже решение разобрано по частям: что стоит на своём месте, зачем это нужно и какие ошибки чаще всего появляются, если часть кода пропустить.

Где хранится роль

Роль должна попасть в JWT при создании token-а, а потом извлекаться сервером при Socket.IO connect. Клиент не должен сам объявлять себя admin в payload события.

  • LoginRequest в учебном варианте может принимать username/password, а роль берётся из серверной demo-логики.
  • create_access_token добавляет claim role в payload JWT.
  • jwt.encode подписывает payload секретным ключом.
  • После подписи клиент не может незаметно изменить role: подпись перестанет совпадать.

Как роль попадает в Socket.IO подключение

  • Клиент передаёт token в Socket.IO auth, например { access_token: token }.
  • connect вызывает authorize_socketio до принятия пользовательских событий.
  • verify_user_token декодирует JWT и возвращает данные пользователя, включая роль.
  • Сервер сохраняет данные в словаре по sid, чтобы последующие events знали, кто подключён.

Как работает admin_message

  • admin_message - отдельное Socket.IO событие, которому нужны права admin.
  • Внутри handler-а сервер берёт пользователя по sid, а не из data клиента.
  • Если role != "admin", событие не выполняет admin-действие и может отправить отказ текущему клиенту.
  • Если роль admin, сервер отправляет admin-сообщение выбранным получателям или текущему клиенту по логике главы.

Что проверять

  • Подключение без token-а должно быть отклонено на этапе connect.
  • Подключение с обычным пользователем должно проходить, но admin_message должен быть запрещён.
  • Подключение с admin token-ом должно пройти и разрешить admin_message.
  • Так ученик видит разницу между проверкой token-а и проверкой прав на конкретное событие.

Читаем авторизованный Socket.IO ответ сверху вниз

  • JWT-константы и helpers идут в начале, потому что они нужны и HTTP login, и Socket.IO connect.
  • create_access_token создаёт token с username и role.
  • verify_user_token делает обратное: проверяет token и возвращает данные пользователя.
  • authorize_socketio адаптирует проверку JWT под Socket.IO auth payload.
  • authorized_clients хранит подтверждённых пользователей по sid.
  • Socket.IO events после connect уже не должны доверять данным клиента о username/role.

Что происходит при connect

  • Клиент подключается и передаёт auth: { access_token: token }.
  • Socket.IO вызывает connect(sid, environ, auth).
  • authorize_socketio достаёт token из auth.
  • verify_user_token проверяет подпись и срок действия JWT.
  • Если token плохой, connect возвращает False, и подключение отклоняется.
  • Если token хороший, сервер сохраняет пользователя в authorized_clients и отправляет authorized.

Почему admin_message проверяется отдельно

  • Успешный connect означает только “пользователь известен”. Это authentication.
  • Право отправлять admin-событие - отдельное правило. Это authorization.
  • Обычный пользователь может быть валидно подключён, но всё равно не иметь права на admin_message.
  • Поэтому handler события должен проверить role перед выполнением действия.
  • Это тот же принцип, что require_admin в REST-главе, только применённый к Socket.IO event.

Короткое резюме решения

  • Authorization для Socket.IO - это не только проверка token-а при connect, но и проверка доступа к конкретному событию.
  • Для сложных правил лучше вынести проверку в отдельную функцию.
