Глава 12: Socket.IO чат, БД и тестирование

Chat API, SQLAlchemy storage, service layer, Socket.IO events и тестовая SQLite-БД.

Порт: 8012 Swagger: http://localhost:8012/docs Результат: После главы вы умеете хранить сообщения чата в БД, отдавать их через REST и отправлять новые сообщения через Socket.IO.

Что разбираем в этой главе

  • TestClient - синхронный клиент для тестирования ASGI-приложения.
  • dependency_overrides - замена production dependency тестовой реализацией.
  • sqlite:// + StaticPool - одна in-memory БД на весь тестовый engine.
  • Service layer - класс ChatService, который можно проверять отдельно.
  • Socket.IO chat event - событие chat_message сохраняет сообщение через тот же service layer.

Как проходит запрос

  1. REST endpoint создаёт группу через ChatService.create_group.
  2. Socket.IO клиент подключается к /socket.io и отправляет join_group.
  3. Клиент отправляет событие chat_message с text, sender и group_id.
  4. Socket.IO handler открывает SQLAlchemy Session и вызывает ChatService.send_message.
  5. Сообщение сохраняется в SQLite и превращается в простой JSON через message_to_dict.
  6. Сервер делает emit в комнату группы, а REST endpoint может потом вернуть ту же запись из БД.

Endpoint-ы для проверки

POST /api/chat/groupsСоздание группы.
GET /api/chat/groupsСписок групп.
POST /api/chat/messagesОтправка сообщения.

    group: Mapped[ChatGroup | None] = relationship(back_populates="messages")


class SendMessageRequest(BaseModel):
    text: str = Field(min_length=1)
    sender: str = Field(min_length=1)
    group_id: int | None = None


class ChatService:
    def __init__(self, db: Session):
        self.db = db

    def send_message(self, text: str, sender: str, group_id: int | None = None) -> Message:
        message = Message(text=text, sender=sender, group_id=group_id)
        self.db.add(message)
        self.db.commit()
        self.db.refresh(message)
        return message


def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()


def get_chat_service(db: Session = Depends(get_db)) -> ChatService:
    return ChatService(db)


socketio_clients: dict[str, str] = {}


def message_to_dict(message: Message) -> dict:
    return {
        "id": message.id,
        "text": message.text,
        "sender": message.sender,
        "group_id": message.group_id,
        "created_at": message.created_at.isoformat(),

@sio.event

    sender = data.get("sender") or socketio_clients.get(sid, "anonymous")

    room = f"group:{group_id}" if group_id is not None else "global"
    await sio.emit("chat_message", payload, room=room)

Если совсем по-простому

В финальной главе один и тот же чат работает двумя способами: через REST API и через Socket.IO события.

REST endpoint и Socket.IO handler используют один ChatService, поэтому правила сохранения сообщений находятся в одном месте.

Тесты по-прежнему подменяют БД через dependency override для REST, а Socket.IO часть показывает, как подключить real-time слой к тому же сервису.

Построчный разбор

@sio.event
Регистрируем Socket.IO событие. Имя функции становится именем события для клиента.
async def chat_message(sid, data)
Сервер обрабатывает событие chat_message, которое прислал Socket.IO клиент.
sender = data.get(...)
Берём отправителя из payload или из имени, сохранённого при set_name.
with SessionLocal() as db
Открываем короткую Session для работы с SQLite внутри real-time события.
service = ChatService(db)
Используем тот же service layer, что и REST endpoint-ы.
service.send_message(...)
Сохраняем сообщение в БД и получаем ORM-объект с id и created_at.
message_to_dict(message)
Превращаем ORM-объект в простой JSON-friendly словарь.
await sio.emit(..., room=room)
Отправляем сохранённое сообщение всем Socket.IO клиентам выбранной комнаты.

Что здесь важно

  • Socket.IO handler использует тот же ChatService, что и REST API, поэтому бизнес-правила не дублируются.
  • Для каждого Socket.IO события открывается короткая Session и закрывается после сохранения сообщения.
  • REST API и Socket.IO смотрят на одну таблицу, поэтому сообщение, отправленное через событие, видно через GET /api/chat/messages.

Типичные ошибки новичков

  • Дублировать сохранение сообщений отдельно для REST и Socket.IO вместо общего ChatService.
  • Держать одну SQLAlchemy Session глобально для всех Socket.IO событий.
  • Отправлять в событие ORM-объект напрямую, не превращая его в простой JSON-словарь.

    def __init__(self, db: Session):

    def send_message(self, text: str, sender: str, group_id: int | None = None) -> Message:
        if group_id is not None and self.db.get(ChatGroup, group_id) is None:
            raise HTTPException(status_code=404, detail="Group not found")
        message = Message(text=text, sender=sender, group_id=group_id)

        self.db.refresh(group)

        return self.db.query(ChatGroup).order_by(ChatGroup.id).all()

Полный разбор ответа

Ниже решение разобрано по частям: что стоит на своём месте, зачем это нужно и какие ошибки чаще всего появляются, если часть кода пропустить.

Почему удаление группы начинается с service layer

Удаление группы - бизнес-операция. Её должны использовать REST endpoint, Socket.IO event и тесты, поэтому логика живёт в ChatService.delete_group, а не копируется в каждом обработчике.

  • def delete_group(self, group_id: int) принимает id группы, потому что это главный входной параметр операции.
  • self.db.get(ChatGroup, group_id) ищет группу по primary key.
  • Если группы нет, сервис бросает HTTPException(status_code=404). Так REST сразу получит правильный HTTP-ответ.
  • Если группа есть, сервис удаляет связанные сообщения и саму группу в одной транзакции.

Почему сначала удаляются сообщения

  • Сообщения ссылаются на группу через group_id.
  • Если удалить группу, а сообщения оставить, в базе появятся записи, которые указывают на несуществующую группу.
  • В учебном решении выбран простой вариант: при удалении группы удаляются и её сообщения.
  • self.db.query(Message).filter(Message.group_id == group_id).delete() удаляет все сообщения выбранной группы.
  • После этого self.db.delete(group) удаляет саму группу, а self.db.commit() сохраняет изменения.

Как REST endpoint использует сервис

  • @fastapi_app.delete("/api/chat/groups/{group_id}", status_code=204) регистрирует HTTP DELETE endpoint.
  • group_id берётся из URL path.
  • service: ChatService = Depends(get_chat_service) даёт endpoint-у готовый сервис с DB session.
  • service.delete_group(group_id) выполняет всю бизнес-логику.
  • Функция ничего не возвращает, потому что status 204 No Content означает успешное удаление без тела ответа.

Как Socket.IO event использует тот же сервис

  • async def delete_group(sid, data) получает payload от Socket.IO клиента.
  • group_id = int(data["group_id"]) явно превращает значение в число, потому что из JSON оно может прийти строкой.
  • with SessionLocal() as db открывает короткую SQLAlchemy session на время события.
  • ChatService(db) создаёт тот же сервис, который использует REST API.
  • await sio.emit("group_deleted", {"group_id": group_id}) сообщает подключённым клиентам, что группа удалена.

Что доказывает тест

  • make_sqlite_override подменяет обычную БД тестовой SQLite-БД, чтобы тест был изолированным.
  • Тест создаёт группу, отправляет в неё сообщение, удаляет группу и потом запрашивает сообщения этой группы.
  • Ожидаемый результат - пустой список. Это доказывает, что удаление затронуло не только группу, но и связанные сообщения.
  • app.dependency_overrides.clear() в finally очищает подмену, чтобы она не влияла на другие тесты.

Читаем итоговое решение сверху вниз

  • Сначала идут imports для FastAPI, SQLAlchemy, Pydantic, datetime и Socket.IO.
  • Потом создаются engine и SessionLocal, потому что они нужны всем операциям с БД.
  • ORM-модели ChatGroup и Message описывают таблицы.
  • Pydantic DTO описывают JSON-ответы REST API.
  • ChatService содержит бизнес-логику: создать группу, отправить сообщение, получить сообщения, удалить группу.
  • REST endpoint-ы вызывают service через dependency.
  • Socket.IO events тоже создают service, но открывают session вручную на время события.

Что происходит при DELETE /api/chat/groups/{group_id}

  • Клиент вызывает HTTP DELETE endpoint с id группы в URL.
  • FastAPI достаёт group_id из path.
  • Dependency get_chat_service создаёт service с DB session.
  • Endpoint вызывает service.delete_group(group_id).
  • Service ищет группу. Если её нет, возвращается 404.
  • Service удаляет сообщения этой группы, потом саму группу, потом делает commit.
  • Endpoint возвращает status 204, потому что удаление прошло успешно и тело ответа не нужно.

Что происходит при Socket.IO delete_group

  • Клиент отправляет Socket.IO event delete_group с group_id.
  • Handler получает data и превращает group_id в int.
  • Handler открывает SQLAlchemy session через with SessionLocal() as db.
  • Handler создаёт ChatService(db) и вызывает тот же delete_group.
  • После успешного удаления сервер отправляет событие group_deleted.
  • REST и Socket.IO используют одну бизнес-логику, поэтому поведение не расходится.

Почему тест устроен именно так

  • Тест сначала подменяет production-БД на тестовую через dependency_overrides.
  • Потом создаёт группу через настоящий REST endpoint, а не руками через SQLAlchemy.
  • Потом создаёт сообщение этой группы, чтобы проверить не пустой случай.
  • Потом удаляет группу через новый DELETE endpoint.
  • Потом запрашивает сообщения группы и ожидает пустой список.
  • Так тест проверяет весь путь: API -> dependency -> service -> database -> API response.

Короткое резюме решения

  • Сначала напишите тест на ожидаемое поведение service method, затем подключайте Socket.IO событие.
  • Решите явно: сообщения удаляются каскадно или получают group_id=None. Для учебного чата проще каскадное удаление.
