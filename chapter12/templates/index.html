Глава 12: Socket.IO чат, БД и тестирование

Chat API, SQLAlchemy storage, service layer, Socket.IO events и тестовая SQLite-БД.

Порт: 8012 Swagger: http://localhost:8012/docs Результат: После главы вы умеете хранить сообщения чата в БД, отдавать их через REST и отправлять новые сообщения через Socket.IO.

Как пользоваться этой главой

Финальная глава собирает REST API, Socket.IO, базу, сервисный слой и тесты в один учебный пример.

Главная мысль: REST и Socket.IO не должны иметь две разные бизнес-логики. Оба слоя вызывают ChatService.

После этой главы вы должны уметь сохранить сообщение через real-time событие и увидеть ту же запись через REST endpoint.

Если вы только начинаете: не перепрыгивайте сразу к ответу. Сначала запустите пример, затем откройте код рядом с этой страницей и проговаривайте каждую строку обычными словами.

Что разбираем в этой главе

  • TestClient - синхронный клиент для тестирования ASGI-приложения.
  • dependency_overrides - замена production dependency тестовой реализацией.
  • sqlite:// + StaticPool - одна in-memory БД на весь тестовый engine.
  • Service layer - класс ChatService, который можно проверять отдельно.
  • Socket.IO chat event - событие chat_message сохраняет сообщение через тот же service layer.

Как проходит запрос

  1. REST endpoint создаёт группу через ChatService.create_group.
  2. Socket.IO клиент подключается к /socket.io и отправляет join_group.
  3. Клиент отправляет событие chat_message с text, sender и group_id.
  4. Socket.IO handler открывает SQLAlchemy Session и вызывает ChatService.send_message.
  5. Сообщение сохраняется в SQLite и превращается в простой JSON через message_to_dict.
  6. Сервер делает emit в комнату группы, а REST endpoint может потом вернуть ту же запись из БД.

Ключевой фрагмент

{% raw %}@sio.event
async def chat_message(sid, data):
    sender = data.get("sender") or socketio_clients.get(sid, "anonymous")
    text = data.get("text") or data.get("message", "")
    group_id = data.get("group_id")
    with SessionLocal() as db:
        service = ChatService(db)
        message = service.send_message(text=text, sender=sender, group_id=group_id)
        payload = {"event": "chat_message", "message": message_to_dict(message)}
    room = f"group:{group_id}" if group_id is not None else "global"
    await sio.emit("chat_message", payload, room=room){% endraw %}

Если совсем по-простому

В финальной главе один и тот же чат работает двумя способами: через REST API и через Socket.IO события.

REST endpoint и Socket.IO handler используют один ChatService, поэтому правила сохранения сообщений находятся в одном месте.

Тесты по-прежнему подменяют БД через dependency override для REST, а Socket.IO часть показывает, как подключить real-time слой к тому же сервису.

Построчный разбор

@sio.event
Регистрируем Socket.IO событие. Имя функции становится именем события для клиента.
async def chat_message(sid, data)
Сервер обрабатывает событие chat_message, которое прислал Socket.IO клиент.
sender = data.get(...)
Берём отправителя из payload или из имени, сохранённого при set_name.
with SessionLocal() as db
Открываем короткую Session для работы с SQLite внутри real-time события.
service = ChatService(db)
Используем тот же service layer, что и REST endpoint-ы.
service.send_message(...)
Сохраняем сообщение в БД и получаем ORM-объект с id и created_at.
message_to_dict(message)
Превращаем ORM-объект в простой JSON-friendly словарь.
await sio.emit(..., room=room)
Отправляем сохранённое сообщение всем Socket.IO клиентам выбранной комнаты.

Что здесь важно

  • Socket.IO handler использует тот же ChatService, что и REST API, поэтому бизнес-правила не дублируются.
  • Для каждого Socket.IO события открывается короткая Session и закрывается после сохранения сообщения.
  • REST API и Socket.IO смотрят на одну таблицу, поэтому сообщение, отправленное через событие, видно через GET /api/chat/messages.

Типичные ошибки новичков

  • Дублировать сохранение сообщений отдельно для REST и Socket.IO вместо общего ChatService.
  • Держать одну SQLAlchemy Session глобально для всех Socket.IO событий.
  • Отправлять в событие ORM-объект напрямую, не превращая его в простой JSON-словарь.

2. Полный service method и endpoint

{% raw %}class ChatService:
    def delete_group(self, group_id: int) -> None:
        group = self.db.get(ChatGroup, group_id)
        if group is None:
            raise HTTPException(status_code=404, detail="Group not found")

        self.db.query(Message).filter(Message.group_id == group_id).delete()
        self.db.delete(group)
        self.db.commit()


@app.delete("/api/chat/groups/{group_id}", status_code=204)
async def delete_group(group_id: int, service: ChatService = Depends(get_chat_service)):
    service.delete_group(group_id){% endraw %}

3. Полное Socket.IO событие

{% raw %}@sio.event
async def delete_group(sid, data):
    group_id = int(data["group_id"])
    with SessionLocal() as db:
        service = ChatService(db)
        service.delete_group(group_id)
    await sio.emit("group_deleted", {"group_id": group_id}){% endraw %}

4. Полный тест

{% raw %}def test_delete_group_removes_group_messages():
    _, override = make_sqlite_override(Base, get_db)

Разбор решения

  • Сначала напишите тест на ожидаемое поведение service method, затем подключайте Socket.IO событие.
  • Решите явно: сообщения удаляются каскадно или получают group_id=None. Для учебного чата проще каскадное удаление.
