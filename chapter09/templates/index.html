Глава 9: WebSockets

Постоянное двустороннее соединение, connection manager, receive loop и broadcast.

Порт: 8009 Swagger: http://localhost:8009/docs Результат: После главы вы умеете принять WebSocket-соединение, хранить клиентов и рассылать сообщения всем участникам.

Что разбираем в этой главе

  • WebSocket - протокол для постоянного двустороннего обмена.
  • Handshake - начальный HTTP-запрос, после которого соединение переключается в WebSocket.
  • Долгое соединение - сервер не закрывает связь после первого ответа, как в обычном REST.
  • accept() - явное принятие соединения сервером.
  • receive_text() - ожидание следующего сообщения клиента.
  • send_json() - отправка JSON-сообщения клиенту по открытому соединению.
  • while True - receive loop, который держит endpoint живым, пока клиент подключён.
  • WebSocketDisconnect - штатное отключение клиента.
  • ConnectionManager - объект, который хранит активные подключения.
  • Broadcast - отправка одного сообщения всем активным клиентам.

Как проходит запрос

  1. Клиент подключается к ws://localhost:8009/ws.
  2. Браузер сначала делает handshake: просит сервер переключить HTTP-соединение в WebSocket.
  3. Сервер вызывает websocket.accept() и создаёт connection id.
  4. Подключение сохраняется в словаре активных клиентов.
  5. Сервер входит в бесконечный цикл приема сообщений.
  6. Внутри цикла receive_text() ждёт текст от конкретного клиента.
  7. Каждое сообщение рассылается всем текущим клиентам.
  8. Когда пользователь закрывает вкладку, FastAPI выбрасывает WebSocketDisconnect.
  9. При отключении connection id удаляется из manager-а.

Полный код простого WebSocket-чата без решения задачи

{% raw %}from uuid import uuid4

from fastapi import FastAPI, WebSocket, WebSocketDisconnect


app = FastAPI(
    title="Глава 9: WebSockets",
    description="Raw WebSocket chat",
    version="1.0.0",
    docs_url="/docs",
    redoc_url="/redoc",
)


class ConnectionManager:
    def __init__(self):
        self.active_connections: dict[str, WebSocket] = {}

    async def connect(self, websocket: WebSocket) -> str:
        await websocket.accept()
        connection_id = str(uuid4())
        self.active_connections[connection_id] = websocket
        await websocket.send_json({
            "event": "connected",
            "connection_id": connection_id,
        })
        return connection_id

    def disconnect(self, connection_id: str) -> None:
        self.active_connections.pop(connection_id, None)

    async def broadcast(self, payload: dict) -> None:
        disconnected: list[str] = []
        for connection_id, websocket in self.active_connections.items():
            try:
                await websocket.send_json(payload)
            except RuntimeError:
                disconnected.append(connection_id)
        for connection_id in disconnected:
            self.disconnect(connection_id)


manager = ConnectionManager()


@app.get("/api/websocket/info")
async def websocket_info():
    return {
        "endpoint": "/ws",
        "connections": len(manager.active_connections),
    }


@app.websocket("/ws")
@app.websocket("/ws/")
async def websocket_endpoint(websocket: WebSocket):
    connection_id = await manager.connect(websocket)
    try:
        while True:
            message = await websocket.receive_text()
            await manager.broadcast({
                "event": "message",
                "connection_id": connection_id,
                "message": message,
            })
    except WebSocketDisconnect:
        manager.disconnect(connection_id)
        await manager.broadcast({
            "event": "disconnected",
            "connection_id": connection_id,
        }){% endraw %}

Если совсем по-простому

Обычный HTTP-запрос короткий: клиент спросил, сервер ответил, соединение закончилось.

WebSocket остаётся открытым. Клиент и сервер могут обмениваться сообщениями много раз.

Для чата серверу нужно помнить, кто сейчас подключён.

REST endpoint обычно проверяют через браузер, curl или Swagger. WebSocket endpoint так не проверяется: нужен WebSocket-клиент.

Адрес WebSocket начинается с ws://, а не с http://. Для HTTPS-сайтов используется wss://.

Главная схема главы: подключиться, сохранить соединение, ждать сообщения в цикле, рассылать сообщения, убрать соединение при отключении.

Что здесь важно

  • WebSocket endpoint не возвращает HTTP response, он живёт пока открыто соединение.
  • @app.websocket("/ws") создаёт не REST endpoint, а отдельный endpoint для WebSocket handshake.
  • websocket.accept() обязателен: до него сервер ещё не принял WebSocket-соединение.
  • ConnectionManager нужен, чтобы endpoint не хранил список клиентов прямо внутри функции.
  • active_connections хранит живые соединения в памяти процесса: ключ - connection_id, значение - объект WebSocket.
  • receive_text() ждёт следующее сообщение от конкретного клиента и не закрывает соединение после одного сообщения.
  • while True нужен, потому что WebSocket-соединение многоразовое: клиент может отправить 1, 10 или 100 сообщений.
  • send_json() сериализует dict в JSON и отправляет его по открытому WebSocket-соединению.
  • Broadcast должен учитывать отключившихся клиентов, иначе отправка может падать.
  • WebSocketDisconnect - нормальная ситуация: пользователь закрыл вкладку, перезагрузил страницу или потерял сеть.
  • disconnect удаляет connection id из словаря, чтобы сервер не считал закрытое соединение активным.
  • /api/websocket/info оставлен обычным HTTP endpoint-ом, чтобы быстро посмотреть состояние manager-а через браузер или Swagger.
  • @app.websocket("/ws/") добавлен рядом с /ws, чтобы лишний слэш в тестере не превращался в 403.
  • Для масштабирования на несколько процессов нужен внешний broker, например Redis Pub/Sub.

Типичные ошибки новичков

  • Забыть await websocket.accept() внутри connect.
  • Не удалить отключившегося клиента из manager-а.
  • Думать, что WebSocket endpoint можно проверить обычным curl как HTTP.
  • Подключаться к http://localhost:8009/ws вместо ws://localhost:8009/ws.
  • Выбрать режим Socket.IO в тестере для обычного WebSocket endpoint-а. Для 9-й главы нужен режим WebSocket.
  • Писать return внутри receive loop после первого сообщения. Тогда соединение закроется слишком рано.
  • Забывать await перед receive_text(), send_json() или broadcast().

1. Что меняем

Команда /who должна обрабатываться внутри receive loop до broadcast. Это команда только для отправителя.

  • Внутри цикла получить текст сообщения.
  • Проверить, равно ли сообщение /who.
  • Если да, отправить ответ только текущему WebSocket.
  • Если нет, оставить обычный broadcast.

6. Как проверить через страницу теста сокетов

Страница http://localhost:8010/socket-tester умеет проверять и Socket.IO, и обычный WebSocket. Для 9-й главы нужен режим обычного WebSocket.

  • Сначала запустите 9-ю главу, например uvicorn chapter09.app.main:app --reload --port 8009 из корня учебника.
  • Откройте http://localhost:8010/socket-tester.
  • В блоке подключения выберите режим WebSocket, а не Socket.IO.
  • В поле URL для готовой главы укажите ws://localhost:8009/ws.
  • Если вы запускаете учебный файл как python main.py и Uvicorn пишет http://127.0.0.1:7001, в тестере укажите ws://localhost:7001/ws.
  • Поле Socket.IO path, Имя пользователя, Комната и Событие для главы 9 не нужны: они относятся к режиму Socket.IO.
  • В поле Сообщение / payload для первой проверки напишите обычный текст hello, без JSON.
  • Нажмите кнопку подключения. В логе должно появиться сообщение connected с connection_id.
  • Отправьте обычный текст, например hello. Сервер должен вернуть JSON с event: "message".
  • Откройте вторую вкладку тестера, подключитесь к тому же URL и отправьте текст из первой вкладки. Сообщение должно прийти в обе вкладки.
  • После выполнения задачи отправьте /who. Ответ connections должен прийти только в ту вкладку, которая отправила команду.
  • Если видите в терминале WebSocket /ws/ 403, значит тестер подключался к адресу со слэшем на конце. В обновлённом примере работают оба адреса: /ws и /ws/.

7. Как подключиться к проекту ученика

Если ученик тренируется в отдельном проекте, на странице тестера меняется только URL. Остальная логика проверки такая же.

  • Запустите свой проект на своём порту, например uvicorn main:app --reload --port 7009.
  • Убедитесь, что в проекте есть endpoint @app.websocket("/ws"). Если путь другой, используйте свой путь.
  • На странице http://localhost:8010/socket-tester выберите режим WebSocket.
  • В URL напишите адрес своего сервиса: ws://localhost:7009/ws.
  • Если ваш терминал показывает порт 7001, пишите ws://localhost:7001/ws.
  • Если ваш endpoint называется, например, /chat, URL будет ws://localhost:7009/chat.
  • В поле сообщения пишите обычный текст: hello. После выполнения задачи можно отправить /who.
  • Если приложение запущено на другом компьютере или в Docker, замените localhost на нужный host.
  • Если тестер пишет ошибку подключения, сначала проверьте, что ваш проект реально открыт: в терминале uvicorn должен быть запущен без traceback.
  • Если URL заканчивается на /ws/, а в коде есть только @app.websocket("/ws"), старый пример может вернуть 403. Либо уберите последний слэш в тестере, либо добавьте второй декоратор @app.websocket("/ws/").
  • Не используйте http:// для обычного WebSocket. Для локального WebSocket нужен адрес с ws://.

Полный разбор ответа

Ниже решение разобрано по частям: что стоит на своём месте, зачем это нужно и какие ошибки чаще всего появляются, если часть кода пропустить.

Где обрабатывать команду /who

Команда /who должна жить внутри receive loop WebSocket endpoint-а, сразу после получения текста от клиента и до broadcast.

  • message = await websocket.receive_text() ждёт следующее сообщение текущего клиента.
  • После этой строки можно проверить, является ли сообщение командой.
  • if message == "/who" отделяет служебную команду от обычного текста чата.
  • Команду нужно обработать до manager.broadcast, иначе она улетит всем как обычное сообщение.
  • continue после ответа на команду нужен, чтобы код не пошёл дальше и не выполнил общий broadcast.

Почему /who добавляется именно в endpoint

  • /who зависит от текста конкретного сообщения, поэтому проверка находится после receive_text().
  • Manager не должен решать, команда это или обычный текст. Его задача проще: хранить подключения и отправлять сообщения.
  • Endpoint знает текущий websocket, поэтому может ответить только отправителю.
  • Если спрятать эту проверку внутрь broadcast, будет сложнее отделить личные команды от сообщений для всех.

Почему ответ отправляется только текущему клиенту

  • await websocket.send_json(...) отправляет JSON именно в текущее соединение.
  • manager.broadcast(...) рассылает payload всем активным соединениям.
  • Количество подключений - это служебная информация для того, кто спросил. Остальным клиентам она не нужна.
  • Так ученик видит разницу между личным ответом и общей рассылкой.

Откуда берётся count

  • manager.active_connections - словарь всех открытых WebSocket-соединений.
  • len(manager.active_connections) считает количество активных подключений прямо сейчас.
  • Это учебная in-memory структура. Если запустить несколько процессов, у каждого будет свой словарь.
  • Для одного учебного приложения на одном Uvicorn-процессе этого достаточно.

Как проверять

  • Откройте один WebSocket-клиент и отправьте /who. Должен прийти JSON с event: "connections".
  • Откройте две вкладки и отправьте /who из одной. Ответ должен прийти только в эту вкладку.
  • Отправьте обычный текст. Он должен по-прежнему прийти всем клиентам через broadcast.
  • Если /who видят все вкладки, значит команда ошибочно отправляется через broadcast.
  • Для ручной проверки удобно использовать http://localhost:8010/socket-tester, режим WebSocket, URL ws://localhost:8009/ws.

Читаем WebSocket-ответ сверху вниз

  • Imports нужны для WebSocket, WebSocketDisconnect и генерации id через uuid4.
  • ConnectionManager держит словарь активных подключений.
  • connect делает сразу три вещи: принимает соединение, создаёт id и сохраняет WebSocket в словарь.
  • Метод connect принимает соединение, сохраняет его и отправляет клиенту служебное сообщение.
  • Метод disconnect удаляет соединение, когда клиент ушёл.
  • Метод broadcast проходит по всем соединениям и отправляет одинаковый payload каждому активному клиенту.
  • websocket_info - обычный HTTP endpoint, который показывает состояние manager-а без WebSocket-клиента.
  • WebSocket endpoint содержит бесконечный receive loop, потому что соединение живёт дольше одного HTTP request.

Что происходит при подключении

  • Клиент открывает адрес ws://localhost:8009/ws.
  • FastAPI вызывает функцию websocket_endpoint.
  • Первой строкой endpoint вызывает manager.connect(websocket).
  • Внутри manager-а выполняется await websocket.accept(), и сервер принимает соединение.
  • Потом создаётся connection_id, например 7c5....
  • Соединение сохраняется в active_connections.
  • Клиент получает первое JSON-сообщение {"event": "connected", "connection_id": ...}.
  • После этого endpoint не завершается, а переходит в while True и ждёт сообщения.

Что происходит внутри receive loop

  • while True означает: пока соединение открыто, сервер ждёт новые сообщения.
  • message = await websocket.receive_text() останавливает выполнение до следующего сообщения клиента.
  • После получения текста сервер проверяет, является ли он командой /who.
  • Если это /who, сервер отвечает только текущему websocket.
  • Если это обычный текст, сервер вызывает manager.broadcast.
  • Если клиент закрывает вкладку, возникает WebSocketDisconnect, и endpoint переходит в cleanup.

Что происходит при обычном сообщении

  • Клиент отправляет текст, например hello.
  • receive_text() возвращает строку hello.
  • Проверка message == "/who" не проходит.
  • Endpoint собирает payload с event, connection_id и message.
  • manager.broadcast проходит по словарю активных соединений.
  • Каждый клиент получает одинаковый JSON.
  • После рассылки цикл возвращается наверх и снова ждёт следующее сообщение.

Почему /who не должен быть broadcast

  • /who - команда управления, а не сообщение чата.
  • Если отправить её всем, другие пользователи увидят техническую команду, которую они не вводили.
  • Личный ответ через websocket.send_json показывает, что сервер может отвечать не только broadcast-ом.
  • Так глава готовит ученика к личным сообщениям, комнатам и авторизации в следующих главах.
  • Обычные сообщения всё равно остаются broadcast, поэтому существующее поведение чата не ломается.

Что происходит при отключении

  • Пользователь закрывает вкладку, обновляет страницу или теряет соединение.
  • await websocket.receive_text() больше не может получить текст и FastAPI выбрасывает WebSocketDisconnect.
  • Код переходит в блок except WebSocketDisconnect.
  • manager.disconnect(connection_id) удаляет соединение из active_connections.
  • После удаления manager делает broadcast события disconnected оставшимся клиентам.
  • Если не удалить соединение, счётчик подключений будет неправильным, а broadcast будет пытаться писать в закрытый WebSocket.

Как использовать socket-tester для своего проекта

  • Страница тестера находится на http://localhost:8010/socket-tester.
  • Для 9-й главы выбирайте режим WebSocket.
  • Для готовой главы URL: ws://localhost:8009/ws.
  • Для проекта ученика URL строится так: ws://localhost:ВАШ_ПОРТ/ВАШ_ПУТЬ.
  • Если проект запущен командой uvicorn main:app --reload --port 7009 и endpoint называется /ws, URL будет ws://localhost:7009/ws.
  • После подключения отправьте обычный текст, затем откройте вторую вкладку и проверьте broadcast.
  • После выполнения задачи отправьте /who и убедитесь, что ответ видит только отправитель.

Короткое резюме решения

  • Команды, предназначенные только отправителю, не нужно рассылать через broadcast.
  • Так появляется первая серверная логика поверх обычного транспорта.
