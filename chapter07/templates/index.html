Глава 7: Authentication и Authorization

Регистрация, вход, password hashing, JWT access token и protected endpoint.

Порт: 8007 Swagger: http://localhost:8007/docs Результат: После главы вы понимаете разницу между проверкой личности и проверкой прав доступа.

Что разбираем в этой главе

  • Authentication - подтверждаем, кто пользователь.
  • Authorization - решаем, разрешено ли пользователю действие.
  • Password hash - пароль нельзя хранить открытым текстом.
  • JWT - подписанный token с claims вроде sub, role и exp.
  • OAuth2PasswordBearer - dependency, которая читает Bearer token из заголовка Authorization.

Как проходит запрос

  1. Пользователь регистрируется через /api/auth/register: отправляет username, email и password.
  2. Сервер проверяет, что username и email ещё не заняты.
  3. Пароль хешируется через pwd_context.hash(...), а не сохраняется как есть.
  4. В demo-хранилище USERS появляется пользователь с password_hash и ролью user.
  5. После регистрации сервер сразу выпускает JWT с username, role и временем истечения.
  6. При JSON-login сервер находит пользователя и проверяет пароль через pwd_context.verify(...).
  7. Swagger Authorize использует отдельный endpoint /api/auth/token, потому что OAuth2 password flow отправляет form-data, а не JSON.
  8. Клиент передаёт token в заголовке Authorization: Bearer ....
  9. Dependency декодирует и проверяет подпись JWT.
  10. Protected endpoint получает текущего пользователя или возвращает 401.

Endpoint-ы для проверки

POST /api/auth/registerСоздание пользователя и выдача token-а.
POST /api/auth/loginJSON login: проверка пароля и выдача token-а.
POST /api/auth/tokenForm login для Swagger Authorize.
GET /api/protectedEndpoint, доступный только с валидным Bearer token.

{% raw %}import os
from datetime import datetime, timedelta, timezone

from fastapi import Depends, FastAPI, HTTPException, status
from fastapi.security import OAuth2PasswordBearer, OAuth2PasswordRequestForm
from jose import JWTError, jwt
from passlib.context import CryptContext
from pydantic import BaseModel


SECRET_KEY = os.getenv("JWT_SECRET_KEY", "fastapi-book-development-secret")
ALGORITHM = "HS256"
ACCESS_TOKEN_EXPIRE_MINUTES = 60
pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")
oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/api/auth/token")
USERS: dict[str, dict] = {}


app = FastAPI(
    title="Глава 7: JWT Authorization",
    description="Authentication and authorization",
    version="1.0.0",
)


class LoginRequest(BaseModel):
    username: str
    password: str


class RegisterRequest(BaseModel):
    username: str
    email: str
    password: str


class AuthResponse(BaseModel):
    access_token: str
    token: str
    token_type: str = "bearer"
    username: str
    role: str
    expires: datetime


def create_access_token(username: str, role: str) -> tuple[str, datetime]:
    expires = datetime.now(timezone.utc) + timedelta(minutes=ACCESS_TOKEN_EXPIRE_MINUTES)
    payload = {"sub": username, "role": role, "exp": expires}
    return jwt.encode(payload, SECRET_KEY, algorithm=ALGORITHM), expires


def build_auth_response(username: str, role: str, token: str, expires: datetime) -> AuthResponse:
    return AuthResponse(
        access_token=token,
        token=token,
        username=username,
        role=role,
        expires=expires,
    )


def authenticate_user(username: str, password: str) -> dict:
    user = USERS.get(username)
    if user is None or not pwd_context.verify(password, user["password_hash"]):
        raise HTTPException(status_code=401, detail="Неверное имя пользователя или пароль")
    return user


def get_current_user(token: str = Depends(oauth2_scheme)) -> dict:
    try:
        payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
        username = payload.get("sub")
    except JWTError as error:
        raise HTTPException(status_code=status.HTTP_401_UNAUTHORIZED, detail="Invalid token") from error
    user = USERS.get(str(username))
    if user is None:
        raise HTTPException(status_code=status.HTTP_401_UNAUTHORIZED, detail="User not found")
    return user


@app.post("/api/auth/register", response_model=AuthResponse)
async def register(request: RegisterRequest):
    if request.username in USERS:
        raise HTTPException(status_code=400, detail="Пользователь с таким именем уже существует")
    if any(user["email"] == request.email for user in USERS.values()):
        raise HTTPException(status_code=400, detail="Пользователь с таким email уже существует")

    USERS[request.username] = {
        "username": request.username,
        "email": request.email,
        "password_hash": pwd_context.hash(request.password),
        "role": "user",
    }
    token, expires = create_access_token(request.username, "user")
    return build_auth_response(request.username, "user", token, expires)


@app.post("/api/auth/login", response_model=AuthResponse)
async def login(request: LoginRequest):
    user = authenticate_user(request.username, request.password)
    token, expires = create_access_token(user["username"], user["role"])
    return build_auth_response(user["username"], user["role"], token, expires)


@app.post("/api/auth/token", response_model=AuthResponse)
async def swagger_login(form_data: OAuth2PasswordRequestForm = Depends()):
    user = authenticate_user(form_data.username, form_data.password)
    token, expires = create_access_token(user["username"], user["role"])
    return build_auth_response(user["username"], user["role"], token, expires)


@app.get("/api/protected")
async def protected(user: dict = Depends(get_current_user)):
    return {"message": "Это защищенный endpoint", "username": user["username"], "role": user["role"]}{% endraw %}

Если совсем по-простому

Сначала пользователь создаётся через регистрацию. Сервер сохраняет не пароль, а password hash.

Потом пользователь доказывает, кто он, через login и пароль. После этого сервер выдаёт token.

Token похож на пропуск: клиент показывает его при каждом защищённом запросе.

Сервер проверяет подпись token-а и понимает, можно ли доверять данным внутри него.

Что здесь важно

  • os.getenv("JWT_SECRET_KEY", ...) берёт secret key из переменной окружения. Если её нет, используется учебное значение. В реальном проекте secret key нельзя хранить прямо в коде.
  • ACCESS_TOKEN_EXPIRE_MINUTES = 60 задаёт срок жизни access token-а. После истечения JWT нельзя использовать для защищённых endpoint-ов.
  • CryptContext(schemes=["bcrypt"]) говорит passlib, каким алгоритмом хешировать пароль.
  • OAuth2PasswordBearer(tokenUrl="/api/auth/token") не логинит пользователя. Он только описывает для FastAPI/Swagger, откуда брать token и как потом читать Authorization: Bearer ....
  • USERS здесь обычный словарь, чтобы не усложнять главу базой данных. Ключ - username, значение - данные пользователя.
  • RegisterRequest описывает JSON, который клиент отправляет при создании пользователя.
  • LoginRequest описывает JSON для обычного login endpoint-а. Поэтому /api/auth/login снова показывает поля username/password в Swagger Try it out.
  • AuthResponse делает ответ регистрации и login одинаковым: token, тип token-а, username, роль и срок действия.
  • access_token нужен Swagger Authorize: окно авторизации ожидает именно это OAuth2-поле.
  • token оставлен как учебный alias того же значения, чтобы новичку было проще видеть “вот token”.
  • create_access_token создаёт payload, добавляет sub, role, exp и подписывает всё через jwt.encode.
  • build_auth_response нужен, чтобы не копировать сборку ответа в register, JSON-login и Swagger-login.
  • /api/auth/login принимает обычный JSON. Его удобно проверять через Try it out.
  • /api/auth/token принимает form-data через OAuth2PasswordRequestForm. Именно туда ходит кнопка Swagger Authorize.
  • authenticate_user вынесен отдельно, чтобы JSON-login и Swagger-login проверяли пароль одинаково.
  • pwd_context.hash(request.password) превращает пароль в hash. В USERS не должно быть открытого пароля.
  • pwd_context.verify(...) при login сравнивает введённый пароль с сохранённым hash.
  • get_current_user запускается до protected endpoint-а, потому что endpoint просит Depends(get_current_user).
  • jwt.decode(...) не просто читает JSON. Он проверяет подпись и срок действия token-а.
  • payload.get("sub") достаёт username из token-а. Endpoint не верит username из запроса клиента.
  • Token не шифруется, а подписывается: содержимое можно прочитать, но нельзя незаметно изменить без secret key.
  • В demo пользователи хранятся в памяти, поэтому после перезапуска они пропадают.
  • Для role-based доступа добавьте отдельную dependency, которая проверяет user['role'].

Типичные ошибки новичков

  • Хранить пароль в открытом виде вместо hash.
  • Пытаться войти через /api/auth/login до регистрации пользователя.
  • Сохранять пароль в ответе API. Клиенту нужен token, а не пароль или password_hash.
  • Нажимать Swagger Authorize до регистрации пользователя: тогда login правильно вернёт 401.
  • Путать /api/auth/login и /api/auth/token: первый принимает JSON, второй form-data для Authorize.
  • Пытаться читать пустой body как JSON. Для новичка проще держать JSON-login и form-login отдельными endpoint-ами.
  • Доверять username, который прислал клиент, вместо username из token-а.
  • Путать 401 и 403: 401 - не вошёл, 403 - вошёл, но прав не хватает.

3. Ключевое место для admin-роли

В полном коде выше это уже встроено в register. Отдельно выделено место, где обычный пользователь отличается от admin.

  • Если username равен admin, учебный код выдаёт роль admin.
  • Для всех остальных username роль остаётся user.
  • Token создаётся уже с выбранной ролью, поэтому require_admin может проверить её позже.

GET /api/adminС admin token вернётся 200.
GET /api/adminС token обычного пользователя вернётся 403.

Полный разбор ответа

Ниже решение разобрано по частям: что стоит на своём месте, зачем это нужно и какие ошибки чаще всего появляются, если часть кода пропустить.

Чем authentication отличается от authorization в ответе

Login отвечает на вопрос “кто ты?”, а admin endpoint отвечает на вопрос “можно ли тебе сюда?”. Поэтому в решении появляются и token, и проверка роли.

  • RegisterRequest получает роль пользователя при регистрации в учебном примере.
  • UserInDb хранит роль на сервере вместе с username, email и hash пароля.
  • create_access_token кладёт роль в JWT payload, чтобы сервер мог прочитать её позже.
  • get_current_user проверяет token и возвращает пользователя, которому сервер доверяет.

Почему роль нельзя брать из запроса к admin endpoint

  • Клиент может отправить любой JSON или query-параметр, например role=admin. Этому нельзя доверять.
  • Роль должна прийти из проверенного источника: базы/памяти сервера или подписанного JWT.
  • jwt.decode проверяет подпись token-а. Если token подделан, декодирование упадёт.
  • После декодирования сервер ищет пользователя в USERS, чтобы убедиться, что такой пользователь всё ещё существует.

Как работает require_admin

  • require_admin - отдельная dependency поверх get_current_user.
  • Сначала FastAPI вызывает get_current_user, получает текущего пользователя, а потом передаёт его в require_admin.
  • Если user.role != "admin", dependency бросает HTTPException(status_code=403).
  • 403 Forbidden означает: пользователь известен, но прав недостаточно.
  • Если проверка пройдена, dependency возвращает user, и endpoint может спокойно выполнить admin-логику.

Что должен доказать тест или ручная проверка

  • Обычный пользователь должен успешно логиниться, но получать 403 на /api/admin.
  • Admin-пользователь должен получать 200 на /api/admin.
  • Запрос без Bearer token должен получить 401, потому что authentication не пройдена.
  • Так ученик видит три разные ситуации: нет входа, вошёл без прав, вошёл с правами.

Читаем auth-ответ сверху вниз

  • Imports нужны для JWT, password hashing, OAuth2 dependency, Pydantic-моделей и HTTP-ошибок.
  • Константы SECRET_KEY, ALGORITHM и время жизни token-а определяют, как создаётся JWT.
  • pwd_context отвечает за hash пароля. Даже в учебнике пароль не должен сравниваться как обычная строка.
  • RegisterRequest описывает body регистрации: username, email и password.
  • LoginRequest описывает body входа: username и password.
  • AuthResponse делает одинаковый формат ответа для регистрации и login.
  • USERS - учебное хранилище в памяти. В реальном проекте здесь была бы таблица users.
  • OAuth2PasswordBearer(tokenUrl="/api/auth/token") связывает кнопку Swagger Authorize с form endpoint-ом /api/auth/token.
  • create_access_token собирает payload и подписывает JWT.
  • build_auth_response возвращает одинаковую структуру JSON из register, login и token endpoint-а.
  • authenticate_user содержит общую проверку username/password, чтобы не копировать её в два login endpoint-а.
  • get_current_user превращает Bearer token обратно в пользователя.
  • require_admin добавляет вторую проверку: не просто вошёл, а вошёл с нужной ролью.

Что происходит при регистрации

  • Клиент отправляет POST /api/auth/register с JSON body.
  • FastAPI проверяет body через RegisterRequest: должны быть username, email и password.
  • Endpoint проверяет, что username ещё не лежит в USERS.
  • Endpoint проверяет, что email ещё не используется другим пользователем.
  • pwd_context.hash(request.password) создаёт password hash. Открытый пароль не сохраняется.
  • В USERS[request.username] сохраняется username, email, password_hash и role.
  • create_access_token(...) создаёт JWT уже после успешного создания пользователя.
  • Ответ возвращается через AuthResponse, поэтому клиент сразу получает token для защищённых endpoint-ов.

Что происходит при login

  • Клиент отправляет POST /api/auth/login с username и password.
  • Endpoint ищет пользователя в USERS по username.
  • Если пользователя нет, возвращается 401: сервер не смог подтвердить личность.
  • Если пользователь есть, pwd_context.verify(...) сравнивает введённый пароль с сохранённым hash.
  • Если пароль неверный, снова возвращается 401.
  • Если пароль верный, сервер создаёт новый JWT и возвращает его клиенту.
  • Этот endpoint принимает JSON, поэтому в Swagger Try it out вы видите нормальное JSON-тело с username/password.

Почему есть /api/auth/login и /api/auth/token

  • /api/auth/login сделан для обычного API-клиента: frontend, curl, Postman или Swagger Try it out отправляют JSON.
  • /api/auth/token сделан для OAuth2 password flow в Swagger Authorize.
  • Swagger Authorize отправляет не JSON, а form-data с полями username и password.
  • Если заставить один endpoint угадывать все форматы вручную, новичку сложнее понимать код и легче получить ошибку JSONDecodeError.
  • Оба endpoint-а вызывают authenticate_user, поэтому логика проверки пароля остаётся в одном месте.
  • Оба endpoint-а возвращают AuthResponse, поэтому наружу приходит одинаковый token.

Что происходит при запросе /api/admin

  • Клиент отправляет header Authorization: Bearer ....
  • OAuth2 dependency достаёт token из header-а.
  • get_current_user декодирует token, проверяет подпись и ищет пользователя.
  • Если token плохой, запрос заканчивается 401 Unauthorized.
  • Если token хороший, FastAPI передаёт user в require_admin.
  • Если user не admin, dependency бросает 403 Forbidden.
  • Если user admin, endpoint admin_area выполняется и возвращает успешный JSON.

Почему 401 и 403 разные

  • 401 означает: сервер не смог подтвердить личность пользователя.
  • 403 означает: сервер знает пользователя, но не разрешает действие.
  • Для новичка это важная граница: authentication проверяет вход, authorization проверяет права.
  • Если всё возвращать как 401, будет непонятно, пользователь не вошёл или вошёл без нужной роли.
  • Если всё возвращать как 403, клиент не поймёт, что ему сначала нужно получить token.

Короткое резюме решения

  • 401 означает, что пользователь не аутентифицирован; 403 - пользователь известен, но прав не хватает.
  • Проверку роли лучше вынести в dependency, чтобы переиспользовать в нескольких endpoint-ах.
