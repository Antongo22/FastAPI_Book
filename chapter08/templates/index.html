Глава 8: Refresh Tokens

Короткий access token, долгоживущий refresh token, rotation, revoke и logout.

Порт: 8008 Swagger: http://localhost:8008/docs Результат: После главы вы понимаете, зачем разделять access и refresh token и почему refresh token нужно хранить на сервере.

Как пользоваться этой главой

Access token живёт недолго, refresh token помогает получить новый access token без повторного ввода пароля.

Главная идея главы - rotation: старый refresh token после обновления становится недействительным, а клиент получает новый.

Сервер хранит refresh token в SQLite, поэтому может отозвать его при logout или при подозрительной активности.

Что разбираем в этой главе

  • Access token - короткоживущий JWT для доступа к API.
  • Refresh token - случайная строка, которая хранится в БД и выпускает новую пару token-ов.
  • Rotation - при refresh старый refresh token отзывается и создаётся новый.
  • Revoke - ручное прекращение действия refresh token-а.
  • Logout - отзыв всех активных refresh token-ов пользователя.

Как проходит запрос

  1. Register/login создаёт пользователя и выдаёт access + refresh token.
  2. Access token живёт недолго и отправляется в Bearer header.
  3. Refresh token хранится в таблице refresh_tokens.
  4. При /api/auth/refresh сервер проверяет token, срок действия и revoked flag.
  5. Старый refresh token отзывается, новая пара token-ов возвращается клиенту.
  6. Повторное использование старого refresh token-а возвращает HTTP 401.

Endpoint-ы для проверки

POST /api/auth/registerСоздание пользователя и первой пары token-ов.
POST /api/auth/loginВход и выдача новой пары token-ов.
POST /api/auth/refreshRotation refresh token-а.
POST /api/auth/revokeОтзыв конкретного refresh token-а.
POST /api/auth/logoutОтзыв всех token-ов текущего пользователя.

Если совсем по-простому

Access token должен жить недолго: если его украдут, ущерб ограничен временем жизни.

Refresh token нужен, чтобы пользователь не вводил пароль каждые 15 минут.

Refresh token хранится на сервере, поэтому его можно отозвать.

Что здесь важно

  • Refresh token не является JWT: это opaque value, смысл которого известен только серверу.
  • Rotation помогает обнаруживать и блокировать повторное использование украденного token-а.
  • В production refresh token обычно хранится в HttpOnly cookie или защищённом хранилище клиента.

Типичные ошибки новичков

  • Не отзывать старый refresh token при обновлении.
  • Делать refresh token JWT без хранения на сервере, а потом не иметь возможности его отозвать.
  • Хранить refresh token в небезопасном месте на клиенте.

Контрольные вопросы

  1. Почему access token делают короткоживущим?

Полное решение задачи

Здесь решение показано как в большом учебнике: что менять, какой код вставлять, где он должен находиться и как проверить результат. Это не только одна функция, а весь минимальный контекст, чтобы новичок не гадал, куда вставлять кусок кода.

1. Что меняем

Нужно добавить поле в ORM-модель refresh token-а и заполнять его во всех местах, где token отзывается.

  • Добавить поле revoked_at в модель RefreshToken.
  • Заполнять revoked_at в /refresh, когда старый token отзывается.
  • Заполнять revoked_at в /revoke.
  • Для logout обновлять все активные token-ы пользователя.

2. Полный фрагмент модели и revoke-логики

{% raw %}class RefreshToken(Base):
    __tablename__ = "refresh_tokens"

    id: Mapped[int] = mapped_column(Integer, primary_key=True)
    token: Mapped[str] = mapped_column(String(255), unique=True, index=True)
    user_id: Mapped[int] = mapped_column(ForeignKey("users.id"))
    expires_at: Mapped[datetime] = mapped_column(DateTime)
    revoked: Mapped[bool] = mapped_column(Boolean, default=False)
    revoked_at: Mapped[datetime | None] = mapped_column(DateTime, nullable=True)
    user: Mapped[User] = relationship(back_populates="refresh_tokens")


def revoke_token(stored: RefreshToken) -> None:
    stored.revoked = True
    stored.revoked_at = datetime.utcnow(){% endraw %}
