Глава 8: Refresh Tokens

Короткий access token, долгоживущий refresh token, rotation, revoke и logout.

Порт: 8008 Swagger: http://localhost:8008/docs Результат: После главы вы понимаете, зачем разделять access и refresh token, как работает rotation и почему refresh token должен храниться на сервере.

Что разбираем в этой главе

  • Access token - короткоживущий JWT для доступа к API.
  • Refresh token - случайная строка, которая хранится на сервере и выпускает новую пару token-ов.
  • In-memory storage - учебное хранение в словаре Python: данные пропадают после перезапуска приложения.
  • Pydantic record - объект состояния token-а: username, expires_at, revoked, revoked_at.
  • Rotation - при refresh старый refresh token отзывается и создаётся новый.
  • Revoke - ручное прекращение действия refresh token-а.
  • Logout - отзыв всех активных refresh token-ов пользователя.

Как проходит запрос

  1. Register/login создаёт пользователя и выдаёт access + refresh token.
  2. Access token живёт недолго и отправляется в Bearer header.
  3. Refresh token хранится в словаре REFRESH_TOKENS как Pydantic-модель StoredRefreshToken.
  4. При /api/auth/refresh сервер проверяет token, срок действия и revoked flag.
  5. Старый refresh token отзывается, новая пара token-ов возвращается клиенту.
  6. Повторное использование старого refresh token-а возвращает HTTP 401.

Endpoint-ы для проверки

POST /api/auth/registerСоздание пользователя и первой пары token-ов.
POST /api/auth/loginВход и выдача новой пары token-ов.
POST /api/auth/refreshRotation refresh token-а.
POST /api/auth/revokeОтзыв конкретного refresh token-а.
POST /api/auth/logoutОтзыв всех token-ов текущего пользователя.

Ключевой фрагмент

{% raw %}import secrets
from datetime import datetime, timedelta, timezone

from fastapi import Depends, FastAPI, HTTPException, status
from fastapi.security import OAuth2PasswordBearer
from jose import JWTError, jwt
from passlib.context import CryptContext
from pydantic import BaseModel


SECRET_KEY = "fastapi-book-development-secret"
ALGORITHM = "HS256"
ACCESS_TOKEN_EXPIRE_MINUTES = 15
REFRESH_TOKEN_EXPIRE_DAYS = 7
pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")
oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/api/auth/login")


app = FastAPI(
    title="Глава 8: Refresh Tokens",
    description="Token rotation and revoke",
    version="1.0.0",
)


class UserRecord(BaseModel):
    username: str
    email: str
    password_hash: str
    role: str = "user"


class StoredRefreshToken(BaseModel):
    token: str
    username: str
    expires_at: datetime
    revoked: bool = False
    revoked_at: datetime | None = None


class RegisterRequest(BaseModel):
    username: str
    email: str
    password: str


class LoginRequest(BaseModel):
    username: str
    password: str


class RefreshTokenRequest(BaseModel):
    refresh_token: str


class AuthResponse(BaseModel):
    access_token: str
    refresh_token: str
    token_type: str = "bearer"
    username: str
    role: str
    access_token_expires: datetime
    refresh_token_expires: datetime


USERS: dict[str, UserRecord] = {}
REFRESH_TOKENS: dict[str, StoredRefreshToken] = {}


def create_access_token(user: UserRecord) -> tuple[str, datetime]:
    expires = datetime.now(timezone.utc) + timedelta(minutes=ACCESS_TOKEN_EXPIRE_MINUTES)
    payload = {"sub": user.username, "username": user.username, "role": user.role, "exp": expires}
    return jwt.encode(payload, SECRET_KEY, algorithm=ALGORITHM), expires


def create_refresh_token(user: UserRecord) -> tuple[str, datetime]:
    token = secrets.token_urlsafe(48)
    expires = datetime.utcnow() + timedelta(days=REFRESH_TOKEN_EXPIRE_DAYS)
    REFRESH_TOKENS[token] = StoredRefreshToken(token=token, username=user.username, expires_at=expires)
    return token, expires


def revoke_refresh_token(stored: StoredRefreshToken) -> None:
    stored.revoked = True
    stored.revoked_at = datetime.utcnow()


def authenticate_user(username: str, password: str) -> UserRecord:
    user = USERS.get(username)
    if user is None or not pwd_context.verify(password, user.password_hash):
        raise HTTPException(status_code=401, detail="Неверное имя пользователя или пароль")
    return user


def get_current_user(token: str = Depends(oauth2_scheme)) -> UserRecord:
    try:
        payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
        username = str(payload["sub"])
    except (JWTError, KeyError) as error:
        raise HTTPException(status_code=status.HTTP_401_UNAUTHORIZED, detail="Invalid token") from error
    user = USERS.get(username)
    if user is None:
        raise HTTPException(status_code=status.HTTP_401_UNAUTHORIZED, detail="User not found")
    return user


@app.post("/api/auth/register", response_model=AuthResponse)
async def register(request: RegisterRequest):
    if request.username in USERS:
        raise HTTPException(status_code=400, detail="Пользователь с таким именем уже существует")
    user = UserRecord(
        username=request.username,
        email=request.email,
        password_hash=pwd_context.hash(request.password),
        role="user",
    )
    USERS[user.username] = user
    access_token, access_expires = create_access_token(user)
    refresh_token, refresh_expires = create_refresh_token(user)
    return AuthResponse(
        access_token=access_token,
        refresh_token=refresh_token,
        username=user.username,
        role=user.role,
        access_token_expires=access_expires,
        refresh_token_expires=refresh_expires,
    )


@app.post("/api/auth/login", response_model=AuthResponse)
async def login(request: LoginRequest):
    user = authenticate_user(request.username, request.password)
    access_token, access_expires = create_access_token(user)
    refresh_token, refresh_expires = create_refresh_token(user)
    return AuthResponse(
        access_token=access_token,
        refresh_token=refresh_token,
        username=user.username,
        role=user.role,
        access_token_expires=access_expires,
        refresh_token_expires=refresh_expires,
    )


@app.post("/api/auth/refresh")
async def refresh(request: RefreshTokenRequest):
    stored = REFRESH_TOKENS.get(request.refresh_token)
    if stored is None or stored.revoked or stored.expires_at <= datetime.utcnow():
        raise HTTPException(status_code=401, detail="Недействительный refresh token")

    revoke_refresh_token(stored)
    user = USERS.get(stored.username)
    if user is None:
        raise HTTPException(status_code=401, detail="Пользователь не найден")
    access_token, access_expires = create_access_token(user)
    refresh_token, refresh_expires = create_refresh_token(user)
    return {
        "access_token": access_token,
        "refresh_token": refresh_token,
        "access_token_expires": access_expires,
        "refresh_token_expires": refresh_expires,
    }{% endraw %}

Если совсем по-простому

Access token должен жить недолго: если его украдут, ущерб ограничен временем жизни.

Refresh token нужен, чтобы пользователь не вводил пароль каждые 15 минут.

В учебной версии refresh token хранится на сервере в словаре, поэтому его можно отозвать без базы данных.

Самое важное: access token доказывает право ходить в защищённые endpoint-ы, а refresh token нужен только для получения новой пары token-ов.

Refresh token нельзя просто принимать на веру. Сервер каждый раз сверяет его со своим словарём.

Что здесь важно

  • Refresh token не является JWT: это opaque value, смысл которого известен только серверу.
  • Opaque value означает “непрозрачное значение”: клиент видит длинную строку, но не может сам прочитать из неё username, роль или срок действия.
  • Access token в этой главе остаётся JWT: он содержит payload, подписывается секретом и проверяется без поиска в словаре.
  • Refresh token сделан другой технологией специально: сервер должен иметь возможность найти его у себя и отозвать в любой момент.
  • USERS - учебное хранилище пользователей. Ключ словаря - username, значение - Pydantic-модель UserRecord.
  • REFRESH_TOKENS - учебное серверное хранилище. Клиент видит только строку token-а, но не видит объект StoredRefreshToken.
  • Ключ в REFRESH_TOKENS - сама строка refresh token-а. Значение - объект, где сервер помнит владельца, срок жизни и состояние отзыва.
  • StoredRefreshToken показывает состояние token-а без БД: кому принадлежит, когда истекает, отозван ли, когда отозван.
  • secrets.token_urlsafe(48) нужен для случайной строки, которую практически невозможно угадать перебором.
  • create_refresh_token не просто возвращает строку клиенту. Сначала он создаёт серверную запись в словаре, и только потом отдаёт token наружу.
  • В /api/auth/refresh есть несколько защитных проверок: token должен существовать, не быть отозванным, не быть просроченным, а пользователь всё ещё должен существовать.
  • revoke_refresh_token меняет Pydantic-объект прямо в словаре.
  • Отдельный commit не нужен, потому что словарь живёт в памяти Python, а не в базе данных.
  • /api/auth/logout проходит по REFRESH_TOKENS.values(), потому что у одного пользователя может быть несколько активных refresh token-ов: браузер, телефон, второй браузер.
  • Rotation помогает обнаруживать и блокировать повторное использование украденного token-а.
  • В production refresh token обычно хранится в HttpOnly cookie или защищённом хранилище клиента.

Типичные ошибки новичков

  • Не отзывать старый refresh token при обновлении.
  • Делать refresh token JWT без хранения на сервере, а потом не иметь возможности его отозвать.
  • Хранить refresh token в небезопасном месте на клиенте.
  • Думать, что словарь заменяет БД в production. Это только учебный способ увидеть механику без лишнего слоя.
  • Пугаться сообщения error reading bcrypt version: это совместимость passlib и новых версий bcrypt, а не ошибка refresh token логики.
  • Если видите error reading bcrypt version, закрепите зависимость bcrypt>=4.0,<4.1 и переустановите зависимости.
  • Получить 401 при повторном /api/auth/refresh со старым refresh token-ом - нормально. Старый token отзывается после первого успешного refresh.

Полное решение задачи

Это ответ именно к задаче из вкладки “Практика”. Здесь показано, что менять, какой код вставлять, где он должен находиться и как проверить результат. Это не только одна функция, а весь минимальный контекст, чтобы новичок не гадал, куда вставлять кусок кода.

1. Что меняем

  • Добавить поле revoked_reason: str | None = None в StoredRefreshToken.
  • Изменить helper revoke_refresh_token, чтобы он принимал reason.
  • При refresh передавать reason rotated.
  • При ручном revoke передавать reason manual.
  • При logout передавать reason logout.

    refresh_token: str


class AuthResponse(BaseModel):
    access_token: str
    refresh_token: str
    token_type: str = "bearer"
    username: str
    role: str
    access_token_expires: datetime
    refresh_token_expires: datetime


USERS: dict[str, UserRecord] = {}
REFRESH_TOKENS: dict[str, StoredRefreshToken] = {}


def create_access_token(user: UserRecord) -> tuple[str, datetime]:
    expires = datetime.now(timezone.utc) + timedelta(minutes=ACCESS_TOKEN_EXPIRE_MINUTES)
    payload = {"sub": user.username, "username": user.username, "role": user.role, "exp": expires}
    return jwt.encode(payload, SECRET_KEY, algorithm=ALGORITHM), expires


def create_refresh_token(user: UserRecord) -> tuple[str, datetime]:
    token = secrets.token_urlsafe(48)
    expires = datetime.utcnow() + timedelta(days=REFRESH_TOKEN_EXPIRE_DAYS)
    REFRESH_TOKENS[token] = StoredRefreshToken(token=token, username=user.username, expires_at=expires)
    return token, expires


def revoke_refresh_token(stored: StoredRefreshToken, reason: str) -> None:
    stored.revoked = True
    stored.revoked_at = datetime.utcnow()
    stored.revoked_reason = reason


def authenticate_user(username: str, password: str) -> UserRecord:
    user = USERS.get(username)
    if user is None or not pwd_context.verify(password, user.password_hash):
        raise HTTPException(status_code=401, detail="Неверное имя пользователя или пароль")
    return user


def get_current_user(token: str = Depends(oauth2_scheme)) -> UserRecord:
    try:
        payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
        username = str(payload["sub"])
    except (JWTError, KeyError) as error:
        raise HTTPException(status_code=status.HTTP_401_UNAUTHORIZED, detail="Invalid token") from error
    user = USERS.get(username)
    if user is None:
        raise HTTPException(status_code=status.HTTP_401_UNAUTHORIZED, detail="User not found")
    return user


@app.post("/api/auth/register", response_model=AuthResponse)
async def register(request: RegisterRequest):
    if request.username in USERS:
        raise HTTPException(status_code=400, detail="Пользователь с таким именем уже существует")
    user = UserRecord(
        username=request.username,
        email=request.email,
        password_hash=pwd_context.hash(request.password),
        role="user",
    )
    USERS[user.username] = user
    access_token, access_expires = create_access_token(user)
    refresh_token, refresh_expires = create_refresh_token(user)
    return AuthResponse(
        access_token=access_token,
        refresh_token=refresh_token,
        username=user.username,
        role=user.role,
        access_token_expires=access_expires,
        refresh_token_expires=refresh_expires,
    )

    refresh_token, refresh_expires = create_refresh_token(user)

        refresh_token=refresh_token,

        role=user.role,
        access_token_expires=access_expires,
        refresh_token_expires=refresh_expires,
    )


@app.post("/api/auth/refresh", response_model=AuthResponse)
async def refresh(request: RefreshTokenRequest):
    stored = REFRESH_TOKENS.get(request.refresh_token)
    if stored is None or stored.revoked or stored.expires_at <= datetime.utcnow():
        raise HTTPException(status_code=401, detail="Недействительный refresh token")
    revoke_refresh_token(stored, reason="rotated")
    user = USERS.get(stored.username)
    if user is None:
        raise HTTPException(status_code=401, detail="Пользователь не найден")
    access_token, access_expires = create_access_token(user)
    refresh_token, refresh_expires = create_refresh_token(user)
    return AuthResponse(
        access_token=access_token,
        refresh_token=refresh_token,
        username=user.username,
        role=user.role,
        access_token_expires=access_expires,
        refresh_token_expires=refresh_expires,
    )


@app.post("/api/auth/revoke")
async def revoke(request: RefreshTokenRequest):
    stored = REFRESH_TOKENS.get(request.refresh_token)
    if stored is not None and not stored.revoked:
        revoke_refresh_token(stored, reason="manual")
    return {"message": "Refresh token отозван"}


@app.post("/api/auth/logout")
async def logout(user: UserRecord = Depends(get_current_user)):
    count = 0
    for stored in REFRESH_TOKENS.values():
        if stored.username == user.username and not stored.revoked:
            revoke_refresh_token(stored, reason="logout")
            count += 1
    return {"message": f"Все сессии завершены. Отозвано токенов: {count}"}{% endraw %}

3. Где использовать revoke_refresh_token

В полном коде выше helper revoke_refresh_token используется во всех местах, где refresh token становится недействительным. Он меняет Pydantic-объект в словаре, поэтому отдельный commit не нужен.

  • В /api/auth/refresh старый token получает reason='rotated'.
  • В /api/auth/revoke token получает reason='manual'.
  • В /api/auth/logout активные token-ы пользователя получают reason='logout'.

4. Почему revoked_reason лежит в StoredRefreshToken

Причина отзыва относится не к пользователю и не к access token-у. Она описывает состояние конкретного refresh token-а, поэтому поле добавляется в StoredRefreshToken.

  • Один пользователь может иметь несколько refresh token-ов.
  • Один token мог быть отозван из-за refresh rotation, второй из-за logout, третий вручную.
  • Если хранить reason в пользователе, мы потеряем информацию по конкретной сессии.
  • Если хранить reason рядом с refresh token-ом, каждая сессия имеет свою историю.

5. Почему helper теперь принимает reason

До задачи helper знал только одно действие: пометить token отозванным. После задачи ему нужно знать причину, потому что разные endpoint-ы отзывают token по разным причинам.

  • refresh передаёт rotated, потому что старый refresh token заменили новым.
  • revoke передаёт manual, потому что клиент явно попросил отозвать token.
  • logout передаёт logout, потому что пользователь завершает сессии.
  • Если reason записывать прямо в каждом endpoint-е вручную, легко забыть сделать это в одном из мест.
  • Поэтому все три endpoint-а вызывают один helper и получают одинаковое поведение.

6. Как проверить

POST /api/auth/registerСоздайте пользователя и сохраните refresh_token из ответа.
POST /api/auth/refreshСтарый refresh token становится revoked=True, получает revoked_at и revoked_reason='rotated'.
POST /api/auth/refreshПовтор старого refresh token-а возвращает 401.
POST /api/auth/logoutВсе активные refresh token-ы текущего пользователя получают revoked_reason='logout'.

Полный разбор ответа

Ниже решение разобрано по частям: что стоит на своём месте, зачем это нужно и какие ошибки чаще всего появляются, если часть кода пропустить.

Зачем StoredRefreshToken

Refresh token - это не только строка. Серверу нужно знать, кому token принадлежит, когда он истекает, отозван ли он и когда был отозван. Поэтому значение в словаре - Pydantic-модель StoredRefreshToken, а не просто строка.

  • token - случайная строка, которую клиент присылает в /api/auth/refresh.
  • username - владелец refresh token-а.
  • expires_at - срок действия refresh token-а.
  • revoked - можно ли ещё использовать token.
  • revoked_at - когда token был отозван.

Что лежит в USERS и REFRESH_TOKENS

В этой главе специально нет базы данных. Всё серверное состояние хранится в двух обычных словарях Python, чтобы новичок видел механику без SQL, миграций и sessions.

  • USERS хранит пользователей: username -> UserRecord.
  • UserRecord хранит email, username, hash пароля и роль.
  • REFRESH_TOKENS хранит refresh-сессии: строка token-а -> StoredRefreshToken.
  • Клиент получает только строку refresh token-а. Полный объект StoredRefreshToken остаётся на сервере.
  • После перезапуска приложения оба словаря очистятся. Это нормально для учебного примера и плохо для production.

Почему refresh token не JWT

JWT удобно проверять без хранения на сервере, но это же делает отзыв сложнее. Для refresh token-а в этой главе важнее контроль со стороны сервера.

  • Access token короткий: если он украден, он скоро протухнет сам.
  • Refresh token долгий: если он украден, сервер должен уметь сразу запретить его повторное использование.
  • Поэтому refresh token здесь - случайная opaque-строка из secrets.token_urlsafe(48).
  • Сервер ищет эту строку в REFRESH_TOKENS и принимает решение по своим данным.
  • Клиент не может поменять username или срок действия refresh token-а, потому что эти данные не лежат внутри строки.

Почему revoke лучше вынести в helper

  • Refresh token отзывается в нескольких местах: при refresh rotation, ручном revoke и logout.
  • Если в каждом месте писать token.revoked = True и token.revoked_at = ... вручную, легко забыть одно из полей.
  • revoke_refresh_token делает оба действия вместе, поэтому поведение становится одинаковым.
  • Helper принимает Pydantic-объект StoredRefreshToken из словаря и меняет его поля.

Как меняется refresh flow

  • Клиент отправляет старый refresh token в /api/auth/refresh.
  • Сервер ищет token в словаре REFRESH_TOKENS.
  • Первая проверка: stored is None. Если записи нет, значит сервер не знает такой refresh token.
  • Вторая проверка: stored.revoked. Если token уже отозван, повторно использовать его нельзя.
  • Третья проверка: stored.expires_at <= datetime.utcnow(). Если срок вышел, обновлять сессию нельзя.
  • Четвёртая проверка идёт чуть ниже: USERS.get(stored.username). Если пользователь удалён, новые token-ы выдавать нельзя.
  • Старый token помечается как отозванный и получает revoked_at.
  • После этого сервер создаёт новую пару: свежий access token и свежий refresh token.
  • Если старый token попробуют использовать повторно, проверка stored.revoked должна вернуть ошибку.

Что происходит при logout

  • Logout защищён через Depends(get_current_user), поэтому сначала FastAPI проверяет access token из Authorization header.
  • После проверки endpoint знает текущего пользователя и может брать user.username с сервера.
  • Код проходит по REFRESH_TOKENS.values(), потому что одному пользователю могли выдать несколько refresh token-ов.
  • Условие stored.username == user.username and not stored.revoked выбирает только активные token-ы текущего пользователя.
  • Каждый найденный token отзывается через helper, а count показывает, сколько сессий реально завершили.

Что проверять

  • После refresh старый refresh token должен иметь revoked=True и непустой revoked_at в словаре.
  • После ручного /api/auth/revoke поле revoked_at тоже должно заполниться.
  • После logout все активные refresh token-ы пользователя должны получить время отзыва.
  • Тест должен смотреть не только HTTP status, но и состояние Pydantic-объекта в REFRESH_TOKENS.

Читаем refresh-token решение сверху вниз

  • Imports включают JWT, hashing, datetime и secrets: БД в этой версии главы нет.
  • secrets нужен именно для refresh token-а, потому что это случайная строка, а не JWT.
  • jwt нужен именно для access token-а, потому что access token подписывается и потом проверяется.
  • CryptContext нужен для паролей: пароль нельзя хранить в открытом виде даже в учебном примере.
  • UserRecord хранит учебного пользователя в словаре USERS.
  • StoredRefreshToken хранит состояние refresh token-а в словаре REFRESH_TOKENS.
  • revoked отвечает на вопрос “можно ли использовать token”.
  • revoked_at отвечает на вопрос “когда token перестал быть действительным”.
  • revoked_reason в задаче добавляется, чтобы было видно не только когда, но и почему token отозвали.
  • Helpers создают access/refresh token-ы, проверяют пользователя и отзывают refresh token-ы.
  • Endpoint-ы login, refresh, revoke, logout используют одни и те же helpers.

Что происходит при регистрации и входе

  • При регистрации клиент отправляет username, email и password.
  • Сервер проверяет, что username ещё не занят.
  • Пароль превращается в hash через pwd_context.hash.
  • Пользователь сохраняется в USERS, где ключом становится username.
  • После этого сервер сразу создаёт access token и refresh token, чтобы пользователю не пришлось логиниться отдельным запросом.
  • При login пользователь уже существует, поэтому сервер не создаёт запись заново, а только проверяет пароль и выдаёт новую пару token-ов.

Что лежит в USERS и REFRESH_TOKENS

  • USERS похож на простую таблицу пользователей, но живёт только в памяти процесса.
  • REFRESH_TOKENS похож на простую таблицу сессий, но тоже живёт только в памяти.
  • Когда вызывается create_refresh_token, в словаре появляется новая запись.
  • Когда вызывается revoke_refresh_token, запись не удаляется, а помечается как отозванная.
  • Это сделано специально: по сохранённой записи можно увидеть историю состояния token-а.
  • Если удалить запись из словаря, ученик уже не увидит, был ли token украден, просрочен или отозван.

Что происходит при refresh rotation

  • Клиент присылает старый refresh token.
  • Сервер ищет его в словаре REFRESH_TOKENS.
  • Сервер проверяет три условия у token-а: token найден, не отозван, срок действия не закончился.
  • Если проверка не прошла, сервер возвращает 401.
  • Если token прошёл первые проверки, сервер смотрит пользователя через USERS.get(stored.username).
  • Это отдельная защита: refresh token мог остаться, а пользователя уже могли удалить.
  • Если проверка прошла, старый token получает revoked=True и revoked_at=datetime.utcnow().
  • В решении задачи старый token дополнительно получает revoked_reason="rotated".
  • Сервер создаёт новый access token и новый refresh token.
  • Новый refresh token попадает в REFRESH_TOKENS как отдельная новая запись.
  • Клиент должен сохранить новую пару и больше не использовать старый refresh token.

Что происходит при revoke и logout

  • /api/auth/revoke получает конкретный refresh token в JSON body.
  • Если token найден и ещё активен, сервер вызывает revoke_refresh_token(stored, reason="manual").
  • Если token не найден, endpoint всё равно возвращает спокойный ответ: для клиента главное, что этот token больше нельзя использовать.
  • /api/auth/logout работает иначе: он не принимает refresh token в body.
  • Logout сначала проверяет access token через Depends(get_current_user).
  • После этого сервер знает username текущего пользователя и проходит по REFRESH_TOKENS.values().
  • Все активные token-ы этого пользователя получают reason="logout".
  • Так logout завершает сразу несколько сессий пользователя, а не только одну строку token-а.

Почему revoked_at важен для обучения

  • Без revoked_at ученик видит только boolean и не понимает историю события.
  • С revoked_at можно посмотреть объект в REFRESH_TOKENS и увидеть, когда именно token был отозван.
  • Это помогает отличить logout, manual revoke и refresh rotation, если потом добавить reason.
  • Так появляется привычка хранить не только состояние, но и audit-информацию.
  • В production такие поля помогают расследовать подозрительные повторные использования refresh token-а.

Что сломается, если перепутать access и refresh

  • Если отправить access token в /api/auth/refresh, сервер не найдёт его в REFRESH_TOKENS и вернёт 401.
  • Если отправить refresh token в Authorization Bearer header, jwt.decode не сможет проверить его как JWT.
  • Access token нужен для доступа к защищённым endpoint-ам.
  • Refresh token нужен только для получения новой пары token-ов.
  • Эта разница специально отражена в коде: access token создаёт jwt.encode, refresh token создаёт secrets.token_urlsafe.

Короткое резюме решения

  • Миграция не нужна, потому что в этой главе нет БД.
  • Тест должен проверять не только HTTP 401, но и состояние объекта в REFRESH_TOKENS.
