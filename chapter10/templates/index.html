Глава 10: SignalR-подобный WebSocket manager

Connection id, direct send, broadcast, groups и JSON-команды поверх WebSocket.

Порт: 8010 Swagger: http://localhost:8010/docs Результат: После главы вы понимаете, как построить более удобный слой real-time общения без SignalR.

Как пользоваться этой главой

Здесь простой WebSocket превращается в более удобный протокол с действиями, группами и адресной отправкой.

SignalR в ASP.NET даёт много удобств из коробки. В FastAPI мы показываем идею вручную, чтобы было понятно, что происходит под капотом.

Обратите внимание на формат сообщений: клиент и сервер должны договориться, какие JSON-поля означают broadcast, join, group send и direct send.

Если вы только начинаете: не перепрыгивайте сразу к ответу. Сначала запустите пример, затем откройте код рядом с этой страницей и проговаривайте каждую строку обычными словами.

Что разбираем в этой главе

  • Connection id - серверный идентификатор конкретного WebSocket-клиента.
  • Direct send - отправка одному подключению.
  • Broadcast - отправка всем подключениям.
  • Group - набор connection id, например комната чата.
  • Action protocol - JSON-команды вроде send_to_group и join.

Как проходит запрос

  1. Клиент подключается к /ws/chat?group=general.
  2. Manager создаёт connection id и добавляет его в группу.
  3. Клиент отправляет JSON с action и message.
  4. Action определяет маршрут сообщения: всем, группе или конкретному connection id.
  5. Manager выбирает получателей и отправляет JSON-событие.
  6. При отключении клиент удаляется из всех групп.

Если совсем по-простому

Глава показывает, как поверх WebSocket сделать более удобный протокол: команды, группы и отправку одному клиенту.

Это учебная замена SignalR: мы вручную делаем часть того, что SignalR обычно берёт на себя.

Главная мысль: WebSocket - транспорт, а правила сообщений вы проектируете сами.

Построчный разбор

elif action == "send_to_group"
Проверяем, какую команду прислал клиент в JSON.
data.get("group", group)
Берём группу из сообщения. Если её нет, используем текущую группу подключения.
await manager.send_to_group(...)
Отправляем payload только участникам выбранной группы.
elif action == "join"
Команда подключения к группе.
manager.groups[...].add(connection_id)
Добавляем текущего клиента в set участников группы.
send_to_connection(...)
Отправляем подтверждение только этому клиенту.
else:
Если action не распознан или равен broadcast, используем поведение по умолчанию.
await manager.broadcast(payload)
Рассылаем сообщение всем активным подключениям.

Что здесь важно

  • Это не полный аналог SignalR: нет автогенерации клиента, backplane и typed hubs.
  • Но учебно видно, какие задачи решает SignalR: хранение клиентов, группы, direct send и события.
  • JSON-протокол проще расширять, чем plain text сообщения из предыдущей главы.

Типичные ошибки новичков

  • Не договориться о формате JSON-команд между клиентом и сервером.
  • Хранить группы списком и получать дубликаты connection id.
  • Не удалять connection id из групп при отключении.

Контрольные вопросы

  1. Что является транспортом, а что является протоколом сообщений?
  2. Почему группы удобно хранить как set connection id?
  3. Что должно произойти при отключении клиента?
  4. Чем broadcast отличается от direct send?

Полное решение задачи

Здесь решение показано как в большом учебнике: что менять, какой код вставлять, где он должен находиться и как проверить результат. Это не только одна функция, а весь минимальный контекст, чтобы новичок не гадал, куда вставлять кусок кода.

1. Что меняем

Добавляем новую команду протокола. Она меняет состояние manager-а и возвращает подтверждение только текущему клиенту.

  • В обработчик action добавить ветку leave.
  • Взять имя группы из JSON или использовать текущую группу.
  • Удалить connection id из set участников.
  • Отправить событие left текущему клиенту.

2. Полный блок обработки action

{% raw %}if action == "send_to_connection":
    await manager.send_to_connection(data["connection_id"], payload)
elif action == "send_to_group":
    await manager.send_to_group(data.get("group", group), payload)
elif action == "join":
    target_group = data.get("group", group)
    manager.groups[target_group].add(connection_id)
    await manager.send_to_connection(connection_id, {"event": "joined", "group": target_group})
elif action == "leave":
    target_group = data.get("group", group)
    manager.groups[target_group].discard(connection_id)
    await manager.send_to_connection(connection_id, {"event": "left", "group": target_group})
else:
    await manager.broadcast(payload){% endraw %}

3. Как проверить

WS /ws/chatОтправьте {"action": "join", "group": "python"}.
WS /ws/chatОтправьте {"action": "leave", "group": "python"} и получите событие left.

Короткая версия решения

    target_group = data.get("group", group)
    manager.groups[target_group].discard(connection_id)

Разбор решения

  • Используйте discard, а не remove, чтобы отсутствие connection id не бросало исключение.
  • После выхода из группы broadcast всем всё ещё может доставлять сообщения этому клиенту.
