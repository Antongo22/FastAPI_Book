Глава 4: Error Handling

HTTPException, custom exception handlers, validation errors и middleware для времени обработки.

Порт: 8004 Swagger: http://localhost:8004/docs Результат: После главы вы умеете отделять ожидаемые ошибки от неожиданных исключений и возвращать единый JSON-формат.

Как пользоваться этой главой

Эта глава учит делать ошибки частью API-контракта. Клиенту нужен понятный status code и стабильный JSON, а не случайный traceback.

Смотрите на обработчики исключений как на общий переводчик: внутри Python случилось исключение, наружу клиент получает аккуратный HTTP-ответ.

После главы вы должны уметь отличать ошибку валидации, ожидаемую бизнес-ошибку и настоящую серверную ошибку.

Если вы только начинаете: не перепрыгивайте сразу к ответу. Сначала запустите пример, затем откройте код рядом с этой страницей и проговаривайте каждую строку обычными словами.

Что разбираем в этой главе

  • HTTPException - ожидаемая ошибка с выбранным HTTP status code.
  • Custom exception - доменное исключение, для которого можно зарегистрировать handler.
  • RequestValidationError - ошибка валидации входных данных FastAPI/Pydantic.
  • Middleware - общий код вокруг запроса, здесь он добавляет X-Process-Time.
  • JSONResponse - ручное формирование тела и status code.

Как проходит запрос

  1. Запрос проходит через middleware, который сохраняет время старта.
  2. Endpoint либо возвращает успешный результат, либо бросает исключение.
  3. FastAPI ищет самый подходящий exception handler.
  4. Handler превращает исключение в JSON-ответ.
  5. Middleware добавляет заголовок времени обработки уже к готовому ответу.
  6. Клиент получает предсказуемую структуру ошибки.

Если совсем по-простому

Ошибка - это не всегда авария. Иногда это нормальная бизнес-ситуация: не найдено, неверные данные, сервис временно недоступен.

FastAPI позволяет перехватывать исключения и возвращать понятный JSON вместо большого traceback.

В этой главе мы учимся делать ошибки предсказуемыми для клиента.

Построчный разбор

@app.exception_handler(DemoError)
Регистрируем обработчик для конкретного типа ошибки.
async def demo_error_handler(request, exc)
Функция получит сам запрос и объект исключения.
request
Из него можно взять путь, headers, query-параметры и другую информацию о запросе.
exc
Это ошибка, которую кто-то бросил через raise DemoError(...).
JSONResponse(...)
Создаём ответ вручную: выбираем status code и тело JSON.
status_code=500
Говорим клиенту, что произошла серверная ошибка.
content={...}
Тело ответа. Клиент получит именно этот JSON.
str(exc)
Превращаем исключение в строку, чтобы показать сообщение.
str(request.url.path)
Добавляем путь, на котором произошла ошибка. Это помогает отладке.

Что здесь важно

  • Handler принимает исходный request, поэтому может добавить path, correlation id или user id.
  • Для бизнес-ошибок лучше возвращать 400/404/409, а не скрывать их как 500.
  • Глобальные handlers помогают держать одинаковый формат ошибок во всём API.

Типичные ошибки новичков

  • Возвращать 200 OK при ошибке. Клиент тогда не поймёт, что запрос не удался.
  • Показывать пользователю внутренний traceback и секретные детали сервера.
  • Ловить вообще все исключения и скрывать настоящие баги без логирования.

Главная практическая задача

Создайте исключение NotReadyError и handler, который возвращает HTTP 503 с сообщением Сервис временно недоступен.

Сначала выполните задачу самостоятельно, затем откройте вкладку “Ответы” и сравните не только код, но и причину такого решения.

Контрольные вопросы

  1. Чем validation error отличается от вашей custom error?
  2. Почему клиенту важно получать стабильную JSON-форму ошибки?
  3. Где лучше логировать путь запроса и время выполнения?
  4. Когда стоит вернуть 400, 404, 422 и 500?

Полное решение задачи

Здесь решение показано как в большом учебнике: что менять, какой код вставлять, где он должен находиться и как проверить результат. Это не только одна функция, а весь минимальный контекст, чтобы новичок не гадал, куда вставлять кусок кода.

1. Что создаём

Добавляем новый тип ошибки, handler для него и demo-endpoint, чтобы можно было увидеть HTTP 503 в Swagger.

  • Создать класс NotReadyError.
  • Зарегистрировать @app.exception_handler(NotReadyError).
  • Добавить endpoint, который бросает эту ошибку для проверки.

2. Полный код ошибки, handler-а и проверки

{% raw %}class NotReadyError(Exception):
    pass


@app.exception_handler(NotReadyError)
async def not_ready_handler(request, exc: NotReadyError):
    return JSONResponse(
        status_code=503,
        content={
            "error": "Сервис временно недоступен",
            "path": str(request.url.path),
        },
    )


@app.get("/api/error-demo/not-ready")
async def not_ready():
    raise NotReadyError(){% endraw %}

3. Как проверить

GET /api/error-demo/not-readyHTTP 503 и JSON с error.
GET /api/error-demo/successHTTP 200, чтобы убедиться, что приложение в целом работает.

Короткая версия решения

{% raw %}class NotReadyError(Exception):
    pass


@app.exception_handler(NotReadyError)
async def not_ready_handler(request, exc: NotReadyError):
    return JSONResponse(status_code=503, content={"error": "Сервис временно недоступен"}){% endraw %}

Разбор решения

  • HTTP 503 подходит для временной недоступности зависимости или сервиса.
  • Если ошибка ожидаемая, её полезно покрыть тестом на status code и JSON-body.
