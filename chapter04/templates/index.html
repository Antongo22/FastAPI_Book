Глава 4: Error Handling

HTTPException, custom exception handlers, validation errors и middleware для времени обработки.

Порт: 8004 Swagger: http://localhost:8004/docs Результат: После главы вы умеете отделять ожидаемые ошибки от неожиданных исключений и возвращать единый JSON-формат.

Что разбираем в этой главе

  • HTTPException - ожидаемая ошибка с выбранным HTTP status code.
  • Custom exception - доменное исключение, для которого можно зарегистрировать handler.
  • RequestValidationError - ошибка валидации входных данных FastAPI/Pydantic.
  • Middleware - общий код вокруг запроса, здесь он добавляет X-Process-Time.
  • JSONResponse - ручное формирование тела и status code.

Как проходит запрос

  1. Запрос проходит через middleware, который сохраняет время старта.
  2. Endpoint либо возвращает успешный результат, либо бросает исключение.
  3. FastAPI ищет самый подходящий exception handler.
  4. Handler превращает исключение в JSON-ответ.
  5. Middleware добавляет заголовок времени обработки уже к готовому ответу.
  6. Клиент получает предсказуемую структуру ошибки.

Если совсем по-простому

Ошибка - это не всегда авария. Иногда это нормальная бизнес-ситуация: не найдено, неверные данные, сервис временно недоступен.

FastAPI позволяет перехватывать исключения и возвращать понятный JSON вместо большого traceback.

В этой главе мы учимся делать ошибки предсказуемыми для клиента.

Построчный разбор

@app.exception_handler(DemoError)
Регистрируем обработчик для конкретного типа ошибки.
async def demo_error_handler(request, exc)
Функция получит сам запрос и объект исключения.
request
Из него можно взять путь, headers, query-параметры и другую информацию о запросе.
exc
Это ошибка, которую кто-то бросил через raise DemoError(...).
JSONResponse(...)
Создаём ответ вручную: выбираем status code и тело JSON.
status_code=500
Говорим клиенту, что произошла серверная ошибка.
content={...}
Тело ответа. Клиент получит именно этот JSON.
str(exc)
Превращаем исключение в строку, чтобы показать сообщение.
str(request.url.path)
Добавляем путь, на котором произошла ошибка. Это помогает отладке.

Что здесь важно

  • Handler принимает исходный request, поэтому может добавить path, correlation id или user id.
  • Для бизнес-ошибок лучше возвращать 400/404/409, а не скрывать их как 500.
  • Глобальные handlers помогают держать одинаковый формат ошибок во всём API.

Типичные ошибки новичков

  • Возвращать 200 OK при ошибке. Клиент тогда не поймёт, что запрос не удался.
  • Показывать пользователю внутренний traceback и секретные детали сервера.
  • Ловить вообще все исключения и скрывать настоящие баги без логирования.

2. Полный API-код после изменения

{% raw %}import time

from fastapi import FastAPI, HTTPException
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse
from pydantic import BaseModel


app = FastAPI(
    title="Глава 4: Error Handling",
    description="Exception handlers and middleware",
    version="1.0.0",
    docs_url="/docs",
    redoc_url="/redoc",
)


class NotReadyError(Exception):
    pass


class DemoError(Exception):
    pass


class ValidationRequest(BaseModel):
    name: str = ""
    age: int = 0


@app.middleware("http")
async def request_logging_middleware(request, call_next):
    started = time.perf_counter()
    response = await call_next(request)
    response.headers["X-Process-Time"] = f"{time.perf_counter() - started:.6f}"
    return response


@app.exception_handler(DemoError)
async def demo_error_handler(request, exc: DemoError):
    return JSONResponse(
        status_code=500,
        content={"error": str(exc), "path": str(request.url.path)},
    )


@app.exception_handler(RequestValidationError)
async def validation_error_handler(request, exc: RequestValidationError):
    return JSONResponse(
        status_code=400,
        content={"error": "Validation failed", "details": exc.errors()},
    )


@app.exception_handler(NotReadyError)
async def not_ready_handler(request, exc: NotReadyError):
    return JSONResponse(
        status_code=503,
        content={
            "error": "Сервис временно недоступен",
            "path": str(request.url.path),
        },
    )


@app.get("/api/error-demo/not-ready")
async def not_ready():
    raise NotReadyError()


@app.get("/api/error-demo/throw")
async def throw_exception():
    raise DemoError("Это тестовое исключение для демонстрации обработки ошибок")


@app.get("/api/error-demo/badrequest")
async def bad_request_demo():
    raise HTTPException(status_code=400, detail="Это пример BadRequest ответа")


@app.post("/api/error-demo/validate")
async def validate_demo(request: ValidationRequest):
    errors: dict[str, str] = {}
    if not request.name:
        errors["name"] = "Имя обязательно"
    if request.age < 0 or request.age > 150:
        errors["age"] = "Возраст должен быть от 0 до 150"
    if errors:
        return JSONResponse(status_code=400, content={"errors": errors})
    return {"message": "Валидация прошла успешно", "data": request.model_dump()}


@app.get("/api/error-demo/success")
async def success():
    return {"message": "Запрос выполнен успешно"}{% endraw %}

3. Как проверить

GET /api/error-demo/not-readyHTTP 503 и JSON с error.
GET /api/error-demo/successHTTP 200, чтобы убедиться, что приложение в целом работает.

Полный разбор ответа

Ниже решение разобрано по частям: что стоит на своём месте, зачем это нужно и какие ошибки чаще всего появляются, если часть кода пропустить.

Где создаётся новое исключение

NotReadyError лучше объявить рядом с другими custom exception-ами главы. Это не HTTP-ответ, а обычный Python-сигнал: внутри приложения произошла понятная ожидаемая ситуация.

  • class NotReadyError(Exception): наследуется от базового Exception, чтобы его можно было бросать через raise.
  • pass означает, что классу не нужны дополнительные поля. Сам тип исключения уже несёт смысл: сервис не готов.
  • Отдельный класс лучше строки вроде raise Exception("not ready"), потому что FastAPI может привязать handler именно к этому типу.
  • Такой подход масштабируется: для разных ошибок можно сделать разные классы и разные HTTP-ответы.

Зачем нужен exception handler

  • @app.exception_handler(NotReadyError) регистрирует функцию, которая будет ловить именно NotReadyError.
  • Handler принимает request, чтобы при необходимости знать путь, пользователя, headers или request id.
  • Handler принимает exc, потому что FastAPI передаёт само исключение. Даже если сейчас оно не используется, сигнатура остаётся стандартной.
  • JSONResponse нужен, когда вы хотите вручную выбрать status code и тело ответа.

Почему status code 503

  • 503 Service Unavailable означает: сервер жив, но нужная часть сервиса временно недоступна.
  • Это отличается от 500: 500 говорит про неожиданную внутреннюю ошибку, а 503 - про ожидаемую временную недоступность.
  • Сообщение Сервис временно недоступен должно лежать в JSON body, чтобы клиент мог показать его пользователю.
  • Если добавить в ответ path, ученик видит, какой endpoint привёл к ошибке. Это удобно для отладки.

Как проверять

  • Добавьте endpoint, который делает raise NotReadyError(), иначе handler не получится вызвать руками.
  • Откройте /api/error-demo/not-ready. Статус должен быть 503, а не 200 и не 500.
  • Проверьте JSON: там должно быть понятное поле с ошибкой, а не HTML-страница traceback.
  • Проверьте другие endpoint-ы главы. Новый handler не должен ломать обычные успешные ответы.

Читаем error handling сверху вниз

  • Imports нужны для трёх разных задач: FastAPI-маршруты, JSON-ответы и типы ошибок.
  • app = FastAPI(...) создаёт приложение, на которое потом навешиваются middleware, handlers и endpoints.
  • Custom exception classes объявляются до handlers, чтобы decorators могли сослаться на эти классы.
  • Middleware стоит отдельно, потому что оно не ловит одну конкретную ошибку, а оборачивает каждый запрос.
  • Exception handlers стоят до или после endpoint-ов не так критично, но новичку проще читать их до endpoint-ов: сначала правила ошибок, потом места, где ошибки возникают.
  • Endpoint not_ready нужен только для демонстрации: он специально бросает NotReadyError.

Что происходит при raise NotReadyError

  • Endpoint начинает выполняться и доходит до строки raise NotReadyError().
  • Обычный return уже не выполняется: исключение прерывает функцию.
  • FastAPI смотрит, есть ли handler для типа NotReadyError.
  • Он находит функцию с decorator @app.exception_handler(NotReadyError).
  • Handler возвращает JSONResponse со status 503.
  • Middleware получает уже готовый ответ, добавляет header времени обработки и отдаёт его клиенту.

Что сломается, если убрать отдельные части

  • Если убрать класс NotReadyError, endpoint не сможет его бросить.
  • Если убрать decorator @app.exception_handler(NotReadyError), ошибка станет обычной необработанной ошибкой.
  • Если вернуть обычный dict из handler без JSONResponse, будет сложнее явно задать status 503.
  • Если поставить status 500, клиент не поймёт, что это временная ожидаемая недоступность.
  • Если не добавить endpoint для проверки, ученику придётся искусственно вызывать ошибку из тестов, а руками проверить будет сложнее.

Короткое резюме решения

  • HTTP 503 подходит для временной недоступности зависимости или сервиса.
  • Если ошибка ожидаемая, её полезно покрыть тестом на status code и JSON-body.
