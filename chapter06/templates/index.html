Глава 6: SQLModel, SQLite и CRUD

SQLModel-модели, Field, Session, select, CRUD endpoint-ы и минимальная Alembic-миграция.

Порт: 8006 Swagger: http://localhost:8006/docs Результат: После главы вы умеете связать FastAPI с SQLite через SQLModel и понимаете, как одна модель может описывать и таблицу, и JSON-схему.

Что разбираем в этой главе

  • SQLModel - библиотека поверх Pydantic и SQLAlchemy: один стиль моделей для API и таблиц.
  • table=True - признак, что класс должен стать таблицей в базе данных.
  • Field - описание поля: валидация для API и настройки колонки для базы.
  • Session - рабочая область для операций с БД: читать, добавить, commit, refresh, удалить.
  • select - SQLModel-способ собрать запрос к таблице.
  • Column(JSON) - когда поле нужно хранить в базе как JSON-структуру.
  • Relationship - связь между таблицами, например продукт и отзывы.
  • Alembic - инструмент миграций схемы БД.

Alembic команды пошагово

Миграция - это Python-файл с инструкциями для изменения структуры базы данных. Например: добавить колонку, удалить колонку, создать таблицу.

Команды Alembic запускаются из папки главы chapter06, потому что там лежит alembic.ini.

alembic revision создаёт новый файл миграции. alembic upgrade head применяет миграции к базе. alembic downgrade -1 откатывает последнюю миграцию назад.

Как проходит запрос

  1. При старте приложения создаётся SQLModel engine для SQLite.
  2. Класс Product(SQLModel, table=True) описывает таблицу products.
  3. Классы ProductCreate, ProductUpdate и ProductRead описывают внешний JSON API.
  4. Dependency get_db открывает SQLModel Session на время запроса.
  5. Endpoint получает Session через Depends.
  6. Для чтения списка используется db.exec(select(Product)).
  7. После db.commit() SQLModel через SQLAlchemy записывает изменения в SQLite.
  8. Когда меняется структура таблицы, команда alembic upgrade head применяет миграцию к файлу базы данных.

Если совсем по-простому

База данных хранит данные дольше, чем живёт один запрос. SQLModel помогает работать с таблицами как с Python-классами.

SQLModel построен поверх SQLAlchemy и Pydantic: поэтому он умеет и таблицы описывать, и JSON проверять.

Session - это рабочая область для операций с БД. Через неё мы добавляем, читаем, сохраняем и удаляем данные.

Отдельные модели ProductCreate, ProductUpdate, ProductRead нужны, чтобы входной и выходной JSON были понятными.

Построчный разбор

class Product(SQLModel, table=True)
Это SQLModel-класс, который станет таблицей products.
id: int | None = Field(default=None, primary_key=True)
Первичный ключ. При создании продукта id ещё нет, поэтому стоит None.
price: Decimal = Field(sa_column=Column(Numeric(10, 2)))
Для денег используем SQLAlchemy-колонку Numeric, но подключаем её через SQLModel Field.
class ProductCreate(SQLModel)
Модель JSON body для создания продукта. Это не таблица, потому что нет table=True.
def get_db()
Dependency-функция, которая выдаёт SQLModel Session на время запроса.
with Session(engine) as db
Создаём новую Session и автоматически закрываем её после запроса.
yield db
Отдаём Session endpoint-у.
response_model=ProductRead
FastAPI отдаст наружу только поля, описанные в модели ответа.
Product(**request.model_dump())
Берём проверенные поля из SQLModel request-модели и создаём объект таблицы.
db.add(product)
Говорим Session: этот объект нужно вставить в таблицу.
db.commit()
Фактически сохраняем изменения в базе.
db.refresh(product)
Обновляем объект, чтобы получить id, выданный базой.
db.exec(select(Product))
SQLModel-способ выполнить SELECT-запрос и получить продукты.
alembic revision -m "add product field"
Создаёт файл миграции, но ещё не меняет базу.
alembic upgrade head
Применяет миграции и реально меняет структуру базы.

Что здесь важно

  • SQLModel, table=True делает класс таблицей, а не только Pydantic-схемой.
  • Field задаёт правила поля: primary key, длину строки, ограничения чисел и настройки колонки.
  • with Session(engine) гарантирует закрытие Session после запроса.
  • response_model не отдаёт наружу лишние поля таблицы.
  • В учебном режиме таблицы создаются автоматически, а Alembic показан как правильный путь для реального проекта.

Типичные ошибки новичков

  • Создать объект, но забыть db.commit(): данные не сохранятся.
  • Поставить table=True на модель запроса ProductCreate. Тогда SQLModel решит, что это ещё одна таблица.
  • Забыть добавить поле в ProductRead: в базе оно будет, но клиент его не увидит.
  • Создать файл миграции, но забыть alembic upgrade head: код уже ждёт новую колонку, а база ещё старая.
  • Держать одну Session глобально на всё приложение.

2. Полный код SQLModel-части

{% raw %}import os
from datetime import datetime
from decimal import Decimal

from fastapi import Depends, FastAPI, HTTPException, status
from sqlalchemy.pool import StaticPool
from sqlmodel import Column, DateTime, Field, Numeric, Session, SQLModel, create_engine, select


DATABASE_URL = os.getenv("DATABASE_URL", "sqlite:///./chapter06.db")


def make_engine(database_url: str):
    connect_args = {"check_same_thread": False} if database_url.startswith("sqlite") else {}
    kwargs = {"connect_args": connect_args}
    if database_url == "sqlite://":
        kwargs["poolclass"] = StaticPool
    return create_engine(database_url, **kwargs)


engine = make_engine(DATABASE_URL)


app = FastAPI(
    title="Глава 6: SQLModel",
    description="SQLite, SQLModel, Alembic, CRUD",
    version="1.0.0",
    docs_url="/docs",
    redoc_url="/redoc",
)


class Product(SQLModel, table=True):
    __tablename__ = "products"

    id: int | None = Field(default=None, primary_key=True)
    name: str = Field(min_length=1, max_length=120)
    category: str = Field(default="general", max_length=80)
    description: str = Field(default="", max_length=500)
    price: Decimal = Field(sa_column=Column(Numeric(10, 2), nullable=False))
    stock: int = Field(default=0, ge=0)
    created_at: datetime = Field(default_factory=datetime.utcnow, sa_column=Column(DateTime, nullable=False))


class ProductRead(SQLModel):
    id: int
    name: str
    category: str
    description: str
    price: Decimal
    stock: int


class ProductCreate(SQLModel):
    name: str = Field(min_length=1, max_length=120)
    category: str = Field(default="general", max_length=80)
    description: str = Field(default="", max_length=500)
    price: Decimal = Field(gt=0)
    stock: int = Field(default=0, ge=0)


class ProductUpdate(SQLModel):
    name: str | None = Field(default=None, min_length=1, max_length=120)
    category: str | None = Field(default=None, max_length=80)
    description: str | None = Field(default=None, max_length=500)
    price: Decimal | None = Field(default=None, gt=0)
    stock: int | None = Field(default=None, ge=0)


def init_db() -> None:
    SQLModel.metadata.create_all(bind=engine)


def get_db():
    with Session(engine) as db:
        yield db


init_db()


@app.get("/api/products", response_model=list[ProductRead])
async def get_products(db: Session = Depends(get_db)):
    return db.exec(select(Product).order_by(Product.id)).all()


@app.get("/api/products/{product_id}", response_model=ProductRead)
async def get_product(product_id: int, db: Session = Depends(get_db)):
    product = db.get(Product, product_id)
    if product is None:
        raise HTTPException(status_code=404, detail="Product not found")
    return product


@app.post("/api/products", response_model=ProductRead, status_code=status.HTTP_201_CREATED)
async def create_product(request: ProductCreate, db: Session = Depends(get_db)):
    product = Product(**request.model_dump())
    db.add(product)
    db.commit()
    db.refresh(product)
    return product


@app.put("/api/products/{product_id}", status_code=status.HTTP_204_NO_CONTENT)
async def update_product(product_id: int, request: ProductUpdate, db: Session = Depends(get_db)):
    product = db.get(Product, product_id)
    if product is None:
        raise HTTPException(status_code=404, detail="Product not found")
    for field, value in request.model_dump(exclude_unset=True).items():
        setattr(product, field, value)
    db.commit()


@app.delete("/api/products/{product_id}", status_code=status.HTTP_204_NO_CONTENT)
async def delete_product(product_id: int, db: Session = Depends(get_db)):
    product = db.get(Product, product_id)
    if product is None:
        raise HTTPException(status_code=404, detail="Product not found")
    db.delete(product)
    db.commit(){% endraw %}

4. Полная Alembic migration

{% raw %}from alembic import op
import sqlalchemy as sa


revision = "0002_add_product_category"
down_revision = "0001_create_products"
branch_labels = None
depends_on = None


def upgrade():
    op.add_column(
        "products",
        sa.Column("category", sa.String(length=80), nullable=False, server_default="general"),
    )


def downgrade():
    op.drop_column("products", "category"){% endraw %}

Полный разбор ответа

Ниже решение разобрано по частям: что стоит на своём месте, зачем это нужно и какие ошибки чаще всего появляются, если часть кода пропустить.

Где появляется новое поле category

Поле категории должно пройти через все SQLModel-слои: таблицу, модель создания, модель обновления, модель ответа, CRUD endpoint-ы и миграцию.

  • Product.category добавляет колонку в SQLModel-таблицу.
  • ProductCreate.category разрешает клиенту передать категорию при создании продукта.
  • ProductUpdate.category разрешает поменять категорию при обновлении.
  • ProductRead.category возвращает категорию наружу в JSON-ответе.
  • Если забыть модель ответа, поле будет в базе, но клиент его не увидит.

Почему нужен default и nullable

  • default="general" даёт понятное значение, если клиент не передал категорию.
  • nullable=False говорит базе: у продукта всегда должна быть категория.
  • В учебной SQLite-БД таблицы создаются автоматически, но в реальном проекте структура меняется через миграции.
  • Если в уже существующей таблице есть старые продукты, миграция должна дать им значение по умолчанию.

Зачем нужна Alembic migration

  • upgrade() описывает движение вперёд: добавить колонку category.
  • downgrade() описывает откат: удалить колонку, если миграцию нужно отменить.
  • Миграция нужна не FastAPI, а базе данных. FastAPI сам не меняет production-схему при каждом запуске.
  • Даже если demo-приложение вызывает SQLModel.metadata.create_all, главе важно показать правильный промышленный путь.

Что делают команды Alembic

  • cd chapter06 переводит терминал туда, где лежит alembic.ini. Без этого Alembic может не найти настройки.
  • alembic current показывает, какая миграция уже применена к текущей базе.
  • alembic revision -m "add product category" создаёт новый Python-файл миграции в alembic/versions.
  • alembic upgrade head запускает функции upgrade() во всех новых миграциях и доводит базу до последней версии.
  • alembic downgrade -1 запускает downgrade() последней миграции и откатывает базу на один шаг назад.
  • alembic history показывает список миграций, чтобы вы понимали порядок изменений базы.

Что проверять после изменения

  • Создайте продукт без category. В ответе должно быть category: "general" или выбранное вами значение по умолчанию.
  • Создайте продукт с category: "books". Ответ должен вернуть именно books.
  • Откройте список продуктов. Категория должна быть у каждого объекта.
  • Запустите cd chapter06, затем alembic upgrade head и alembic current, чтобы проверить, что миграция применена.
  • Запустите тесты CRUD с тестовой БД, чтобы убедиться, что изменения не завязаны на локальный файл SQLite.

Читаем SQLModel-ответ сверху вниз

  • Imports SQLModel нужны для SQLModel, Field, Session, select и настроек колонок.
  • DATABASE_URL задаёт адрес базы. По умолчанию используется SQLite-файл главы.
  • engine знает, как подключаться к базе, а Session(engine) открывает рабочую сессию.
  • SQLModel.metadata знает, какие таблицы описаны через table=True.
  • Product описывает таблицу, а ProductCreate, ProductUpdate, ProductRead описывают JSON снаружи.
  • Endpoint-ы не должны напрямую знать все детали таблицы. Они работают через session и модели.

Почему category проходит через несколько классов

  • SQLModel-таблица отвечает за хранение в базе: без Product.category колонка не появится в таблице.
  • Create schema отвечает за входные данные при создании: без ProductCreate.category клиент не сможет прислать категорию.
  • Update schema отвечает за частичное изменение: без ProductUpdate.category категорию нельзя будет обновить.
  • Read schema отвечает за выходной JSON: без ProductRead.category клиент не увидит категорию в ответе.
  • Migration отвечает за реальную схему уже существующей базы: без Alembic production-база не узнает про новую колонку.

Что происходит при создании продукта

  • Клиент отправляет POST /api/products с JSON body.
  • FastAPI валидирует body через ProductCreate.
  • Endpoint создаёт ORM-объект Product(**request.model_dump()) или аналогичную конструкцию.
  • SQLModel Session добавляет объект через db.add.
  • db.commit() сохраняет строку в SQLite.
  • db.refresh(product) подтягивает id и значения по умолчанию из базы.
  • FastAPI возвращает объект через ProductRead, и в JSON появляется category.

Короткое резюме решения

  • Менять нужно и SQLModel-таблицу, и входные/выходные модели, иначе поле либо не сохранится, либо не попадёт в публичный ответ.
  • В миграции используйте op.add_column, а в downgrade - op.drop_column.
