Глава 6: SQLAlchemy, DTO и SQLite

Engine, Session, ORM-модель, Pydantic DTO, CRUD endpoint-ы и минимальная Alembic-миграция.

Порт: 8006 Swagger: http://localhost:8006/docs Результат: После главы вы умеете связать FastAPI с SQLite и отделять публичные DTO от внутренних ORM-классов.

Что разбираем в этой главе

  • Engine - подключение SQLAlchemy к базе данных.
  • Session - unit of work: через неё читаем, добавляем, изменяем и удаляем строки.
  • DeclarativeBase - база для ORM-классов.
  • Mapped / mapped_column - типизированное описание колонок SQLAlchemy 2.
  • DTO - Pydantic-модели для входного и выходного JSON.
  • Alembic - инструмент миграций схемы БД.

Как проходит запрос

  1. При старте приложения создаётся engine и sessionmaker.
  2. Dependency get_db открывает Session на время запроса.
  3. Endpoint получает Session через Depends.
  4. ORM-модель Product описывает таблицу products.
  5. Pydantic DTO проверяет входные данные и форматирует выходной JSON.
  6. После commit SQLAlchemy записывает изменения в SQLite.

Endpoint-ы для проверки

GET /api/productsСписок продуктов.
GET /api/products/{product_id}Один продукт или 404.
POST /api/productsСоздание продукта с DTO-валидацией.

Ключевой фрагмент

{% raw %}def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()


@app.post("/api/products", response_model=ProductDto, status_code=201)
async def create_product(request: CreateProductDto, db: Session = Depends(get_db)):
    product = Product(**request.model_dump())
    db.add(product)
    db.commit()
    db.refresh(product)
    return product{% endraw %}

Если совсем по-простому

База данных хранит данные дольше, чем живёт один запрос. SQLAlchemy помогает работать с таблицами как с Python-объектами.

Session - это рабочая область для операций с БД. Через неё мы добавляем, читаем, сохраняем и удаляем данные.

DTO нужны, чтобы внешний JSON API не зависел напрямую от внутренней ORM-модели.

Построчный разбор

def get_db()
Dependency-функция, которая выдаёт подключение к БД на время запроса.
db = SessionLocal()
Создаём новую Session. Через неё endpoint будет работать с БД.
try:
Начинаем блок, где Session отдаётся endpoint-у.
yield db
Отдаём Session наружу. После завершения запроса выполнение вернётся сюда.
finally:
Этот блок выполнится даже если в endpoint-е случилась ошибка.
db.close()
Закрываем Session, чтобы не держать ресурсы.
response_model=ProductDto
FastAPI отдаст наружу только поля, описанные в DTO.
Product(**request.model_dump())
Берём проверенные поля из DTO и создаём ORM-объект.
db.add(product)
Говорим Session: этот объект нужно вставить в таблицу.
db.commit()
Фактически сохраняем изменения в базе.
db.refresh(product)
Обновляем объект, чтобы получить id, выданный базой.

Что здесь важно

  • yield dependency гарантирует закрытие Session после запроса.
  • response_model не отдаёт наружу лишние ORM-поля.
  • В учебном режиме таблицы создаются автоматически, а Alembic показан как правильный путь для реального проекта.

Типичные ошибки новичков

  • Создать объект, но забыть db.commit(): данные не сохранятся.
  • Вернуть ORM-модель без DTO и случайно раскрыть лишние поля.
  • Держать одну Session глобально на всё приложение.

Практическая задача

Добавьте поле category в продукт, DTO и Alembic-миграцию. Проверьте, что оно возвращается в GET /api/products.

Сначала выполните задачу самостоятельно, затем откройте вкладку “Ответы” и сравните не только код, но и причину такого решения.

Полное решение задачи

Здесь решение показано как в большом учебнике: что менять, какой код вставлять, где он должен находиться и как проверить результат. Это не только одна функция, а весь минимальный контекст, чтобы новичок не гадал, куда вставлять кусок кода.

1. Что меняем

Поле category должно пройти через все слои: ORM-модель, DTO для ответа, DTO для создания, DTO для обновления и миграцию.

  • В Product добавить колонку category.
  • В ProductDto добавить поле category.
  • В CreateProductDto добавить обязательное или default-поле.
  • В UpdateProductDto добавить optional-поле.
  • Создать Alembic migration с op.add_column.

2. Полный набор изменений в моделях

{% raw %}class Product(Base):
    __tablename__ = "products"

    id: Mapped[int] = mapped_column(Integer, primary_key=True, index=True)
    name: Mapped[str] = mapped_column(String(120), nullable=False)
    category: Mapped[str] = mapped_column(String(80), default="general")
    description: Mapped[str] = mapped_column(String(500), default="")
    price: Mapped[Decimal] = mapped_column(Numeric(10, 2), nullable=False)
    stock: Mapped[int] = mapped_column(Integer, default=0)
    created_at: Mapped[datetime] = mapped_column(DateTime, default=datetime.utcnow)


class ProductDto(BaseModel):
    id: int
    name: str
    category: str
    description: str
    price: Decimal
    stock: int

    model_config = {"from_attributes": True}


class CreateProductDto(BaseModel):
    name: str = Field(min_length=1)
    category: str = "general"
    description: str = ""
    price: Decimal = Field(gt=0)
    stock: int = Field(ge=0)


class UpdateProductDto(BaseModel):
    name: str | None = None
    category: str | None = None
    description: str | None = None
    price: Decimal | None = Field(default=None, gt=0)
    stock: int | None = Field(default=None, ge=0){% endraw %}

Разбор решения

  • Менять нужно и ORM-модель, и DTO, иначе поле либо не сохранится, либо не попадёт в публичный ответ.
  • В миграции используйте op.add_column, а в downgrade - op.drop_column.
