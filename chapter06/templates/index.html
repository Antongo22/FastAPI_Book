Глава 6: SQLModel, SQLite и CRUD

SQLModel-модели, Field, Session, select, CRUD endpoint-ы и полный Alembic-пайплайн.

Порт: 8006 Swagger: http://localhost:8006/docs Результат: После главы вы умеете связать FastAPI с SQLite через SQLModel и понимаете, как вести миграции Alembic в учебном и стороннем проекте.

Что разбираем в этой главе

  • SQLModel - библиотека поверх Pydantic и SQLAlchemy: один стиль моделей для API и таблиц.
  • table=True - признак, что класс должен стать таблицей в базе данных.
  • Field - описание поля: валидация для API и настройки колонки для базы.
  • AsyncSession - асинхронная рабочая область для операций с БД: читать, добавить, commit, refresh, удалить.
  • create_async_engine - создаёт асинхронное подключение SQLAlchemy к базе.
  • aiosqlite - async-драйвер SQLite; без него URL sqlite+aiosqlite:///... не заработает.
  • greenlet - техническая зависимость, которая нужна SQLAlchemy для async-операций.
  • select - SQLModel-способ собрать запрос к таблице.
  • Column(JSON) - когда поле нужно хранить в базе как JSON-структуру.
  • Relationship - связь между таблицами, например продукт и отзывы.
  • Alembic - инструмент миграций схемы БД.
  • alembic.ini - файл настроек Alembic; команды обычно запускаются из папки, где он лежит.
  • env.py - файл, который подключает Alembic к моделям приложения и SQLModel.metadata.
  • revision - отдельный Python-файл миграции с функциями upgrade() и downgrade().

Alembic команды пошагово в этой главе

Миграция - это Python-файл с инструкциями для изменения структуры базы данных. Например: добавить колонку, удалить колонку, создать таблицу.

Команды Alembic запускаются из папки главы chapter06, потому что там лежит alembic.ini.

alembic revision создаёт новый файл миграции. alembic upgrade head применяет миграции к базе. alembic downgrade -1 откатывает последнюю миграцию назад.

# Создать пустой файл миграции, куда вы вручную вставите upgrade/downgrade
alembic revision -m "add product category"

# Применить все новые миграции до последней версии
alembic upgrade head

# Посмотреть историю миграций
alembic history

# Откатить последнюю миграцию назад
	alembic downgrade -1{% endraw %}

Alembic в стороннем проекте: полный пайплайн

В своём проекте не пишите cd chapter06. Вместо этого перейдите в корень своего проекта: туда, где лежит app/, requirements.txt или pyproject.toml.

Первый раз Alembic нужно инициализировать командой alembic init alembic. Она создаст alembic.ini, папку alembic/, файл alembic/env.py и папку alembic/versions/.

После инициализации нужно подключить Alembic к моделям. Для SQLModel это обычно означает: импортировать все модели и поставить target_metadata = SQLModel.metadata в alembic/env.py.

Не используйте относительный импорт вида from ..main.models import Product. Alembic запускает env.py как отдельный файл, поэтому такой импорт часто падает с ошибкой ImportError: attempted relative import.

Пайплайн всегда один: поменяли SQLModel-код, создали revision, прочитали файл миграции глазами, применили alembic upgrade head, проверили приложение и тесты.

Как проходит запрос

  1. При импорте приложения создаётся async engine для SQLite, но таблицы приложение само не создаёт.
  2. Класс Product(SQLModel, table=True) описывает таблицу products.
  3. Классы ProductCreate, ProductUpdate и ProductRead описывают внешний JSON API.
  4. Перед запуском приложения команда alembic upgrade head создаёт или обновляет таблицы.
  5. Dependency get_db открывает SQLModel AsyncSession на время запроса.
  6. Endpoint получает AsyncSession через Depends.
  7. Для чтения списка используется await db.exec(select(Product)).
  8. После await db.commit() SQLModel через SQLAlchemy записывает изменения в SQLite.
  9. Когда меняется структура таблицы, сначала меняется SQLModel-код, потом создаётся Alembic revision, потом команда alembic upgrade head применяет миграцию к базе данных.

Если совсем по-простому

База данных хранит данные дольше, чем живёт один запрос. SQLModel помогает работать с таблицами как с Python-классами.

SQLModel построен поверх SQLAlchemy и Pydantic: поэтому он умеет и таблицы описывать, и JSON проверять.

AsyncSession - это асинхронная рабочая область для операций с БД. Через неё мы добавляем, читаем, сохраняем и удаляем данные.

Отдельные модели ProductCreate, ProductUpdate, ProductRead нужны, чтобы входной и выходной JSON были понятными.

Построчный разбор

class Product(SQLModel, table=True)
Это SQLModel-класс, который станет таблицей products.
id: int | None = Field(default=None, primary_key=True)
Первичный ключ. При создании продукта id ещё нет, поэтому стоит None.
price: Decimal = Field(sa_column=Column(Numeric(10, 2)))
Для денег используем SQLAlchemy-колонку Numeric, но подключаем её через SQLModel Field.
class ProductCreate(SQLModel)
Модель JSON body для создания продукта. Это не таблица, потому что нет table=True.
async_sessionmaker(...)
Фабрика, которая будет создавать новую AsyncSession для каждого запроса.
async def get_db()
Dependency-функция, которая выдаёт SQLModel AsyncSession на время запроса.
async with AsyncSessionLocal() as db
Создаём новую AsyncSession и автоматически закрываем её после запроса.
yield db
Отдаём AsyncSession endpoint-у.
response_model=ProductRead
FastAPI отдаст наружу только поля, описанные в модели ответа.
Product(**request.model_dump())
Берём проверенные поля из SQLModel request-модели и создаём объект таблицы.
db.add(product)
Говорим AsyncSession: этот объект нужно вставить в таблицу.
await db.commit()
Фактически сохраняем изменения в базе.
await db.refresh(product)
Обновляем объект, чтобы получить id, выданный базой.
await db.exec(select(Product))
SQLModel-способ выполнить SELECT-запрос и получить продукты через async-сессию.
alembic init alembic
Один раз создаёт папку миграций в стороннем проекте.
target_metadata = SQLModel.metadata
Связывает Alembic с SQLModel-моделями для autogenerate.
alembic revision -m "add product field"
Создаёт файл миграции, но ещё не меняет базу.
alembic revision --autogenerate -m "add product field"
Создаёт файл миграции на основе сравнения моделей и текущей БД, но файл всё равно нужно проверить вручную.
alembic upgrade head
Применяет миграции и реально меняет структуру базы.

Что здесь важно

  • SQLModel, table=True делает класс таблицей, а не только Pydantic-схемой.
  • Field задаёт правила поля: primary key, длину строки, ограничения чисел и настройки колонки.
  • async with AsyncSessionLocal() открывает async-сессию и закрывает её после запроса.
  • await db.commit() нужен, потому что запись в БД выполняется асинхронно.
  • response_model не отдаёт наружу лишние поля таблицы.
  • Таблицы создаёт Alembic. Перед запуском приложения выполните cd chapter06 && alembic upgrade head.

Типичные ошибки новичков

  • Создать объект, но забыть await db.commit(): данные не сохранятся.
  • Поставить table=True на модель запроса ProductCreate. Тогда SQLModel решит, что это ещё одна таблица.
  • Забыть добавить поле в ProductRead: в базе оно будет, но клиент его не увидит.
  • Создать файл миграции, но забыть alembic upgrade head: код уже ждёт новую колонку, а база ещё старая.
  • Оставить автосоздание таблиц в runtime-коде и думать, что миграции работают.
  • Держать одну AsyncSession глобально на всё приложение.

После alembic init alembic откройте alembic/env.py и замените файл полностью. Важные части: добавляем папку проекта в sys.path, импортируем Product из main.py, подключаем SQLModel.metadata и передаём Alembic обычный sync URL базы.

  • Не используйте from ..main.models import Product: в простом учебном проекте это часто падает.
  • from main import SYNC_DATABASE_URL, Product нужен, чтобы Alembic увидел URL базы и зарегистрировал таблицу products в metadata.
  • target_metadata = SQLModel.metadata нужен для --autogenerate.
{% raw %}from logging.config import fileConfig

import sys

from alembic import context
from sqlalchemy import engine_from_config, pool
from sqlmodel import SQLModel

PROJECT_ROOT = Path(__file__).resolve().parents[1]
sys.path.insert(0, str(PROJECT_ROOT))

from main import SYNC_DATABASE_URL, Product

config = context.config
config.set_main_option("sqlalchemy.url", SYNC_DATABASE_URL)

if config.config_file_name is not None:
    fileConfig(config.config_file_name)


target_metadata = SQLModel.metadata


def run_migrations_offline() -> None:
    url = config.get_main_option("sqlalchemy.url")
    context.configure(
        url=url,
        target_metadata=target_metadata,
        literal_binds=True,
        dialect_opts={"paramstyle": "named"},
    )

    with context.begin_transaction():
        context.run_migrations()


def run_migrations_online() -> None:
    connectable = engine_from_config(
        config.get_section(config.config_ini_section, {}),
        prefix="sqlalchemy.",
        poolclass=pool.NullPool,
    )

    with connectable.connect() as connection:
        context.configure(connection=connection, target_metadata=target_metadata)

        with context.begin_transaction():
            context.run_migrations()


if context.is_offline_mode():
    run_migrations_offline()
else:
    run_migrations_online(){% endraw %}

5. Если появилась ошибка Target database is not up to date

Эта ошибка означает: в папке alembic/versions уже есть миграция, но текущая база ещё не применена до последней версии. Alembic не даёт создать новую autogenerate-миграцию поверх базы, которая отстаёт.

6. Если появилась ошибка NameError: name 'sqlmodel' is not defined

Эта ошибка появляется не из-за FastAPI и не из-за вашего endpoint-а. Её вызывает migration-файл, который Alembic создал через --autogenerate. Внутри файла есть sqlmodel.sql.sqltypes.AutoString(...), но наверху нет import sqlmodel.

  • Откройте файл в alembic/versions, который был создан командой alembic revision --autogenerate.
  • Найдите импорты вверху файла.
  • Добавьте строку import sqlmodel рядом с import sqlalchemy as sa.
  • После этого снова выполните alembic upgrade head.

7. Если появилась ошибка Table 'products' is already defined

Эта ошибка обычно появляется, когда файл запускают как python main.py, а внутри файла дополнительно вызывают uvicorn.run("main:app", reload=True). Тогда Python сначала выполняет файл как __main__, а потом Uvicorn импортирует этот же файл как модуль main. Модель Product объявляется два раза, и SQLModel пытается зарегистрировать таблицу products второй раз.

  • Не добавляйте extend_existing=True: это замаскирует симптом, но не объяснит причину.
  • Уберите блок if __name__ == "__main__" из учебного main.py, если он у вас остался.
  • Запускайте приложение отдельной командой uvicorn main:app --reload --port 7001 из папки, где лежит main.py.
  • Если сервер уже запущен после неудачной попытки, остановите его через Ctrl+C и запустите правильную команду заново.
{% raw %}# Не так:
python main.py

# Так:
uvicorn main:app --reload --port 7001{% endraw %}

Этот фрагмент не обязателен для поля category, но показывает импорт и синтаксис, который часто нужен в реальных моделях: JSON-колонка и связь между таблицами.

12. Как проверить

Полный разбор ответа

Ниже решение разобрано по частям: что стоит на своём месте, зачем это нужно и какие ошибки чаще всего появляются, если часть кода пропустить.

Где появляется новое поле category

Поле категории должно пройти через общий базовый класс, таблицу, модель создания, модель обновления, модель ответа, CRUD endpoint-ы и миграцию.

  • ProductBase.category описывает общее поле один раз.
  • Product(ProductBase, table=True) наследует поле и превращает его в колонку таблицы.
  • ProductCreate(ProductBase) наследует поле и разрешает клиенту передать категорию при создании продукта.
  • ProductRead(ProductBase) наследует поле и возвращает категорию наружу в JSON-ответе.
  • ProductUpdate.category остаётся отдельным optional-полем, потому что при частичном обновлении клиент может прислать только одно поле.
  • Если забыть модель ответа, поле будет в базе, но клиент его не увидит.

Почему нужен default и nullable

  • default="general" даёт понятное значение, если клиент не передал категорию.
  • nullable=False говорит базе: у продукта всегда должна быть категория.
  • ProductBase убирает повтор одинаковых полей между таблицей, схемой создания и схемой ответа.
  • ProductUpdate не наследуется от ProductBase, потому что в update все поля optional, а в base часть полей обязательная.
  • В этой главе таблицы создаются миграциями. Если миграцию не применить, endpoint-ы будут обращаться к таблице, которой ещё нет.
  • Если в уже существующей таблице есть старые продукты, миграция должна дать им значение по умолчанию.

Зачем нужна Alembic migration

  • upgrade() описывает движение вперёд: добавить колонку category.
  • downgrade() описывает откат: удалить колонку, если миграцию нужно отменить.
  • Миграция нужна не FastAPI, а базе данных. FastAPI сам не меняет production-схему при каждом запуске.
  • FastAPI не создаёт production-схему сам. Для структуры таблиц здесь используется Alembic.

Как Alembic подключается к стороннему проекту

  • alembic init alembic создаёт служебные файлы миграций в вашем проекте.
  • alembic.ini хранит базовые настройки, включая путь к папке миграций и часто URL базы.
  • alembic/env.py запускается каждый раз, когда вы вызываете alembic revision, upgrade или downgrade.
  • Для SQLModel в env.py нужно импортировать модели с table=True, иначе SQLModel.metadata будет пустой или неполной.
  • target_metadata = SQLModel.metadata говорит Alembic, с какой схемой Python-кода сравнивать текущую базу при --autogenerate.
  • Если модели лежат прямо в main.py, не используйте from ..main.models. Добавьте корень проекта в sys.path и импортируйте from main import Product.
  • Если приложение использует sqlite+aiosqlite:///..., Alembic должен получить sync-вариант URL: sqlite:///.... Поэтому в примере есть SYNC_DATABASE_URL.

Что делают команды Alembic

  • cd chapter06 переводит терминал туда, где лежит alembic.ini. Без этого Alembic может не найти настройки.
  • alembic current показывает, какая миграция уже применена к текущей базе.
  • alembic revision -m "add product category" создаёт новый Python-файл миграции в alembic/versions.
  • alembic revision --autogenerate -m "add product category" сравнивает текущую БД и target_metadata, а потом предлагает код миграции.
  • alembic upgrade head запускает функции upgrade() во всех новых миграциях и доводит базу до последней версии.
  • alembic downgrade -1 запускает downgrade() последней миграции и откатывает базу на один шаг назад.
  • alembic history показывает список миграций, чтобы вы понимали порядок изменений базы.

Что проверять после изменения

  • Создайте продукт без category. В ответе должно быть category: "general" или выбранное вами значение по умолчанию.
  • Создайте продукт с category: "books". Ответ должен вернуть именно books.
  • Откройте список продуктов. Категория должна быть у каждого объекта.
  • Запустите cd chapter06, затем alembic upgrade head и alembic current, чтобы проверить, что миграция применена.
  • Запустите тесты CRUD с тестовой БД, чтобы убедиться, что изменения не завязаны на локальный файл SQLite.

Читаем SQLModel-ответ сверху вниз

  • Imports SQLModel нужны для SQLModel, Field, select и настроек колонок, а AsyncSession нужен для async-работы с БД.
  • DATABASE_URL задаёт адрес базы. По умолчанию используется SQLite-файл главы.
  • engine знает, как подключаться к базе, а AsyncSessionLocal() открывает рабочую async-сессию.
  • SQLModel.metadata знает, какие таблицы описаны через table=True.
  • ProductBase хранит общие поля, чтобы не копировать name, category, description, price и stock в несколько классов.
  • Product наследуется от ProductBase и описывает таблицу, потому что у него есть table=True.
  • ProductCreate и ProductRead тоже наследуются от ProductBase, но остаются JSON-схемами, потому что у них нет table=True.
  • ProductUpdate стоит отдельно, потому что все его поля optional для частичного обновления.
  • Endpoint-ы не должны напрямую знать все детали подключения. Они работают через async session и модели.

Почему category проходит через несколько классов

  • ProductBase.category - одно место, где описано общее поле категории.
  • SQLModel-таблица наследует это поле: без Product(ProductBase, table=True) колонка не появится в таблице.
  • Create schema наследует это поле: без ProductCreate(ProductBase) клиент не сможет прислать категорию.
  • Update schema отвечает за частичное изменение: без ProductUpdate.category категорию нельзя будет обновить.
  • Read schema наследует это поле: без ProductRead(ProductBase) клиент не увидит категорию в ответе.
  • Migration отвечает за реальную схему уже существующей базы: без Alembic production-база не узнает про новую колонку.

Что происходит при создании продукта

  • Клиент отправляет POST /api/products с JSON body.
  • FastAPI валидирует body через ProductCreate.
  • Endpoint создаёт ORM-объект Product(**request.model_dump()) или аналогичную конструкцию.
  • SQLModel AsyncSession добавляет объект через db.add.
  • await db.commit() сохраняет строку в SQLite.
  • await db.refresh(product) подтягивает id и значения по умолчанию из базы.
  • FastAPI возвращает объект через ProductRead, и в JSON появляется category.

Короткое резюме решения

  • Менять нужно и SQLModel-таблицу, и входные/выходные модели, иначе поле либо не сохранится, либо не попадёт в публичный ответ.
  • В миграции используйте op.add_column, а в downgrade - op.drop_column.
  • Перед запуском приложения примените миграции: cd chapter06 && alembic upgrade head.
  • CRUD endpoint-ы работают через AsyncSession, поэтому операции записи выполняются с await.
